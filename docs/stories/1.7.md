## Story

**As an admin,**
**I want to be told when something needs me,**
**so that a broken mailbox or a failed send does not sit unnoticed.**

## Acceptance criteria

1. A `notifications` table is tenant-scoped, RLS-forced, keyed per recipient user, with `type`, `title`, `body`, `entity_type`, `entity_id`, `read_at`, `created_at`.
2. `notify(userIds, type, …)` is the single entry point; no feature writes the table directly.
3. The shell shows a bell with an unread count and a panel listing notifications newest-first; clicking one marks it read and navigates to its entity.
4. Owners and admins additionally receive transactional email via Resend for **exactly two** conditions — mailbox connection broken, outbound message `dead` — deduplicated per condition per mailbox within a 24-hour window (FR56).
5. Email sending failure is logged and never blocks the in-app notification, which remains the durable record.
6. A notification that duplicates a conversation timeline event links to it rather than restating it; the timeline stays the source of truth (§6.7).

---

## ⚠ The in-app write and the email go on opposite sides of the commit

Story 1.5 establishes that `audit()` writes **inside** the caller's transaction — an audit row committed separately can record a change that rolled back. **The email half is the mirror image and needs the opposite treatment.**

| | Where | Why |
|---|---|---|
| `notifications` row | **Inside** the transaction, on the same `tx` | If the mailbox-failure write rolls back, the notification must vanish with it |
| Resend email | **After commit**, fire and forget | An email cannot be rolled back. Send it inside the transaction and a rollback leaves an admin told about something that never happened — and there is no way to un-tell them |

Same principle — never announce what did not happen — and opposite mechanisms, because one store has transactions and the other has an outbox somebody else owns.

AC5 falls straight out of this: the email is already outside the transaction, so its failure cannot block anything. Log it and move on.

- [ ] `server/services/notify.ts`, the single entry point. Takes the caller's `tx`.
- [ ] **No feature writes `notifications` directly.** The rule matters for the same reason `audit()`'s does: three later stories will want notifications, and if each writes its own insert they diverge on shape and nobody owns the semantics.
- [ ] For conversation-scoped events, the notification stores `entity_type` and `entity_id` pointing at the `conversation_events` row — **it links, it does not restate** (AC6). One event, one record, two surfaces.

### Task 3 — Bell and panel (AC3)

- [ ] In the shell from Story 1.6. Unread count from the partial index; panel newest-first.
- [ ] Clicking marks read **and** navigates. Marking read on open would clear the badge for things the user never looked at.
- [ ] Poll on the same 10s SWR cycle as the inbox counts (§9.3) — not a separate request.

### Task 4 — Operational email (AC4, AC5)

- [ ] Resend. `RESEND_API_KEY` is already in §12; add it to `server/env.ts` here, since this is the story that first uses it.
- [ ] **Exactly two conditions.** Mailbox connection broken; outbound message `dead`. Not escalations, not assignments — §1.5 puts Slack, Teams, and push out of scope, and the discipline that keeps that true is refusing to widen this list.
- [ ] Audience is owners and admins, resolved through Story 1.5's roles.
- [ ] **Dedup per condition per mailbox within 24h.** Upstash Redis is in §3 for exactly this — a key like `notify:{tenant}:{condition}:{mailbox}` with a 24h TTL, set-if-absent. Without it a broken mailbox polled every 2 minutes sends 720 emails a day, which trains admins to filter the alert that matters.
- [ ] Dispatch **after commit**, failure logged only.

## Dev notes

### The table — [Architecture §6.9](../architecture/database-schema.md)

```sql
CREATE TABLE notifications (
  tenant_id   uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  user_id     uuid NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
  type        text NOT NULL,        -- assigned, escalated, mailbox_broken, send_failed
  title       text NOT NULL,
  body        text,
  entity_type text,                 -- conversation, mailbox, outbound_message
  entity_id   uuid,
  read_at     timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_notifications_unread
  ON notifications (tenant_id, user_id, created_at DESC)
  WHERE read_at IS NULL;
```

`user_id` references `users`, which is global and unpoliced — but `notifications` carries `tenant_id` and **is** policed, so a user in two tenants sees each tenant's notifications only when scoped to it. That is the intended behaviour, not an oversight.

### What the four consumers expect

| Consumer | Surface |
|---|---|
| Epic 2, Story 2.2 — revoked mailbox grant | In-app **+ email** |
| Epic 3, Story 3.4 — assignment | In-app |
| Epic 5, Story 5.4 — escalation | In-app. *Not* a channel — FR48's signed `conversation.escalated` webhook already serves a tenant wanting Slack |
| Epic 6, Story 6.1 — outbox row `dead` | In-app **+ email** |

### Standards

- **§15.6** — `RESEND_API_KEY` is read in `server/env.ts` and nowhere else.
- **§15.9** — a failed send throws a taxonomy class, caught and logged, never surfaced to the caller.
- **§15.10** — if a Workflow step calls `notify()`, assume it runs at least twice. The Redis dedup key makes the email idempotent; the in-app row needs its own guard or a natural key.
