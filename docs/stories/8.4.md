## Story

**As a buyer's security reviewer, I want the controls documented and tested, so that I can approve the purchase.**

## Acceptance criteria

1. Security headers (CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`) are set and verified by test.
2. The prompt-injection corpus passes on every release.
3. Data export and deletion endpoints work, with deletion cascading to blobs within 30 days.
4. A penetration test is completed and findings are remediated or accepted with rationale.
5. Data region is a tenant attribute, and the audit trail satisfies a standard DPA review.

## 🔴 AC3's 30-day window has nowhere to live, and the cron that depends on it was declared without it

§13.1 has always specified *"tenant delete cascades; blob purge job; **30-day soft-delete window**"*, and `/api/cron/purge-blobs` was declared on 2026-08-05 with `tenantsDueForBlobPurge` assigned to this story. §12 requires that enumerator to *"return only tenants whose soft-delete window has **definitively** elapsed"*.

**`tenants` has no `deleted_at`.** Its columns are `id, name, slug, clerk_org_id, plan, status, settings, region, timezone, created_at`. There is `status`, which is a lifecycle value, not a timestamp — **you cannot compute "30 days have elapsed" from it.**

So the enumerator has no predicate to write, and the safest implementation available today is one that returns nothing (harmless) or one that guesses from `status` alone (**deletes a live tenant's attachments**, irreversibly, which §12 names as the worst failure in the cron set).

Fourth instance this week of a column three documents assume and none defines — after `content_hash`, `tenants.timezone`, and `api_keys.scopes`. **The tell is consistent: a phrase in a spec that contains a unit.** "30-day window", "the tenant's timezone", "content hash", "scoped keys" — each names a quantity, and a quantity needs somewhere to be.

```sql
ALTER TABLE tenants
  ADD COLUMN deleted_at timestamptz,
  ADD COLUMN deletion_requested_by text;   -- Clerk user id, for the audit trail
```

`deleted_at` is when the tenant **requested** deletion, not when purging happens. The window is `deleted_at + interval '30 days' < now()`, and it is the only thing `tenantsDueForBlobPurge` may select on.

**And the refusal path §12 requires becomes writable**: a purge run whose candidate count exceeds a sanity threshold stops rather than proceeding. With no `deleted_at` there was no count to sanity-check.

## FR54 and NFR15 pull in opposite directions, and a reviewer will ask

- **FR54**: a tenant can request **full deletion**.
- **NFR15**: audit events are **immutable to the application role** — `audit_events` has `SELECT, INSERT` and no `UPDATE` or `DELETE` grant.

A full tenant delete cascades on the `tenant_id` foreign key, which runs as the **table owner** during the parent delete — so the audit rows go, despite the application role being unable to delete them.

**That is correct, and it should be written down rather than discovered.** The immutability NFR15 buys is *"the application cannot rewrite history"*, not *"records are indestructible"*. GDPR erasure is a deliberate, owner-level act with its own audit trail — and the record that a tenant was deleted **must survive the deletion**, which means it cannot live in that tenant's own `audit_events`.

**Ruling: a tenant-deletion record outside tenant scope.** One row, no personal data — tenant id, requested-at, completed-at, requester — retained after the cascade, because a compliance question a year later is *"prove you deleted them"* and the proof cannot have been deleted too.

## AC1 is the smallest criterion here and CSP is the one that breaks in production only

Headers are a `next.config.ts` change and a test asserting they are present — genuinely small. **CSP is not**, for one reason: Story 3.3 renders sanitized email HTML in a **sandboxed iframe with a strict CSP**, and email HTML is arbitrary.

A CSP tight enough for the app and loose enough for the iframe is two policies, not one. The iframe gets its own, and Story 3.3's warning stands: **never pair `allow-scripts` with `allow-same-origin`**, which re-grants everything the sandbox removed.

**The test asserts the headers on a real response**, not the config object — a config that is correct and not applied is the failure mode a config assertion cannot see.

## AC2 runs a corpus this story does not own

Story 5.2 builds the adversarial corpus and the tool boundary; Story 5.6 puts a one-click run of it in the playground; Story 7.4 extends it with tenant-action responses. **This story makes it a release gate**, which is the one thing none of them do.

§14.6 lists it as non-negotiable. The difference between "runs in CI" and "passes on every release" is a release checklist item — and given §14's note that the nightly eval *does not* block merges, it is worth being explicit that **this one does.**

## AC5 is already satisfied, and the reason is worth quoting to a reviewer

§6.8d ruled data residency: single region, `region text NOT NULL DEFAULT 'us-east' CHECK (region IN ('us-east'))`. The architecture notes the DPA answer directly — *"one region, recorded per tenant, enforced by constraint"* — which reviews better than a routing layer nobody has exercised.

**This story's job is to have that answer written where a reviewer reads it**, not to build anything. §13.1's control table is that place.

## AC3's export is the largest deliberate data egress in the product

Deletion gets the attention; **export is the half that hands a complete copy of a tenant's data to whoever asked.**

- **It is `owner` only.** Not `admin` — an admin can already read everything through the UI, and a downloadable archive is a different risk from paginated access.
- **Delivered as a signed, short-lived, single-use URL**, generated after the export completes, never a synchronous download of an unbounded dataset.
- **It is itself an audit event** (Story 1.5's write path, inside the transaction), because "who exported everything, and when" is the first question after an incident.
- **The archive must not contain other tenants' data**, which sounds trivial and is exactly what a cross-tenant test asserts — the export runs inside `withTenant()` like everything else, and it is the one query set where a mistake copies rather than exposes.
