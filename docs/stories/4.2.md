## Story

**As a developer, I want documents split into retrievable units, so that retrieval returns focused context.**

## Acceptance criteria

1. Text is extracted from each supported format, preserving heading structure where available.
2. Chunks target ~500 tokens with ~15% overlap and do not split mid-heading-section.
3. Token counts are recorded per chunk.
4. Extraction failures set an error status with a readable message rather than leaving the source pending.
5. A fixture corpus of messy real-world documents chunks without crashing or producing empty chunks.

---

## This story is pure functions, and that is the point

Testing strategy §1 lists "parsers, chunkers, RRF" as the unit-test tier. Extraction and chunking take bytes and return an array — no database, no network, no tenant. **They are the only part of Epic 4 that can be tested exhaustively for the price of a fixture file**, which is what makes AC5 affordable.

Keep them that way. `extract(buffer, mimeType) → { text, headings }` and `chunk(text, headings) → Chunk[]`. Story 4.3 owns everything that touches a row or a network.

Fetching is **not** here — Story 4.1 fetches and validates the URL, because the fetch is the security boundary and it belongs with the rest of the source-creation controls.

## AC2's two constraints conflict, and the resolution order matters

"~500 tokens with ~15% overlap" and "do not split mid-heading-section" cannot both hold for a heading section of 3,000 tokens. **Sections win as the primary boundary; the token target is a target.** Split oversized sections at paragraph boundaries and carry the heading path onto every piece, so a chunk retrieved from the middle of a long section still says what it is about.

`metadata` (jsonb, §6.2) carries the heading path — it is what Story 4.5 AC2 shows and what Epic 5's citations quote.

## `content_hash` is computed here and persisted by 4.3

Story 4.1 creates the column. This story fills it: hash the **chunk's normalised content**, not the raw slice — leading/trailing whitespace and line-ending differences must not change the hash, or a document re-saved on Windows re-embeds in full and FR27's "skipping unchanged content" delivers nothing.

Normalisation is part of the hash function's contract and gets its own unit test, because a hash that changes for a reason nobody intended is indistinguishable from a document that changed.

---

## ⚠ AC4 and AC5 name the loud failure. The one that matters is quiet

AC4 covers extraction *failing* — a corrupt PDF, an unreadable encoding. That sets `status = 'error'` with a message, which is right and visible.

**A source that extracts successfully to zero usable chunks sets `status = 'indexed'` with a chunk count of 0.** It is not an error at any layer: the fetch returned 200, the parser returned a string, the chunker returned `[]`, the workflow completed. The sources list shows a green badge.

Three ordinary documents do this:

| Input | Extracts to |
|---|---|
| A scanned PDF — pages of images, no text layer | `""` |
| A JavaScript-rendered documentation page fetched as HTML | a nav shell and a `<noscript>` line |
| A DOCX whose body is one large embedded table or image | whitespace |

The first is the common one. An admin uploads the scanned policy handbook, sees `indexed`, and reasonably concludes the bot knows it. **Retrieval then returns nothing from it, drafts are grounded in less than the admin believes, and there is no error anywhere in the system to find.** NFR23 prohibits exactly this shape — "silent AI failures are prohibited" — and this failure is upstream of the AI, so nothing in Epic 5 catches it.

AC5's wording is what exposed it: *"without crashing or producing empty chunks"*. The chunker is already required not to emit empty chunks — so a document with no text produces **zero** chunks, cleanly, and the requirement is satisfied by the outcome that hides the problem.

**Ruling: zero chunks is a terminal state of its own, not a success.**

`status = 'empty'` — added to Story 4.1's CHECK list — with a message naming the likely cause per source type ("this PDF has no text layer; it may be a scan"). It is not `error`, because nothing went wrong and a Retry button would be a lie. It is not `indexed`, because nothing is indexed.

Below a floor, say fewer than 20 extracted characters, treat it as empty rather than trusting a chunk of `"​ "`. The threshold is a constant with a test, not a feeling.

## Tasks

### Task 1 — Extractors (AC1, AC4)

- [ ] PDF, DOCX, MD, TXT, HTML, plus the FAQ pair (a `Q`/`A` shape, not a parse).
- [ ] Preserve heading structure where the format has one. HTML and MD do; TXT does not, and must not have one inferred.
- [ ] HTML extraction drops nav, script, and style before text — otherwise every page's chunks are 40% site chrome and retrieval matches the menu.
- [ ] Failures throw a typed error (§10.5) carrying a message an admin can act on.

### Task 2 — Chunker (AC2, AC3)

- [ ] Section-first, then ~500 tokens with ~15% overlap within a section.
- [ ] Heading path onto every chunk's `metadata`.
- [ ] `token_count` from the same tokeniser the embedding model uses — a count from a different tokeniser is a number that is right about nothing.

### Task 3 — Content hash (supports FR27)

- [ ] Normalise, then hash. Normalisation tested independently.

### Task 4 — The empty-extraction floor (AC5)

- [ ] Below the character floor → `status = 'empty'` with a per-type message. Not `error`, not `indexed`.

### Task 5 — Fixture corpus (AC5)

- [ ] Messy real documents: a scanned PDF, a JS-rendered page's HTML, a DOCX with tables, a 400-page PDF, a file with mixed encodings, an HTML page that is one `<table>`.
- [ ] Committed to the repo. **A fixture corpus described in a task and not committed is the same defect this project has hit five times** — it must be files, not a plan for files.
