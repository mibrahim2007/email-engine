## Story

**As a business, I want usage-based billing, so that revenue tracks value delivered.**

## Acceptance criteria

1. Messages processed, AI replies, and tokens are recorded per tenant per period.
2. Usage is reported to Stripe on an hourly rollup.
3. Plans define seat counts, message limits, model tiers, and feature access.
4. Subscribe, upgrade, downgrade, and invoice history work end-to-end.
5. Exceeding a plan limit degrades gracefully with clear notice, rather than failing silently or hard-stopping ingest.

## 🔴 An accumulating rollup cannot be retried, and this one bills money

`usage_records` is `(tenant_id, period, metric, quantity)` where `period` is `'YYYY-MM'`. AC2 rolls up **hourly**. So an hourly job writes into a monthly bucket, which can only mean read-modify-write:

```sql
UPDATE usage_records SET quantity = quantity + $n
WHERE tenant_id = $1 AND period = $2 AND metric = $3
```

Three failures, all of which cost or lose money:

1. **There is no unique constraint on `(tenant_id, period, metric)`.** So there is no upsert target — the first run of a period matches zero rows and silently records nothing, or an `INSERT` fallback creates a second row and every later `UPDATE` hits one of two.
2. **Two rollups racing lose an update.** `quantity + $n` read outside a lock is the textbook case, and `tenantsDueForUsageRollup` running long enough to overlap the next hour is not exotic.
3. **The job is not retryable, and NFR18 requires every pipeline step to be.** Re-run an hour after a partial failure and the same usage is added twice — **the tenant is overbilled, and nothing downstream disagrees.**

**Ruling: record at the point of use; aggregate at rollup. Never accumulate in the cron.**

- **Usage is written where it happens** — the ingest workflow records a `messages_processed` event, the agent records `ai_replies` and token counts from the Gateway's per-request report (§10.4) — each carrying the **id of the row that caused it**.
- **The rollup is a pure aggregation** over that period's events, plus a report. It reads, sums, and reports. **Re-running it produces the same number**, which is what makes it retryable, and NFR18 is satisfied by construction rather than by care.
- `usage_records` gains `UNIQUE (tenant_id, period, metric)` regardless, so the aggregate has one row to land on:

```sql
INSERT INTO usage_records (tenant_id, period, metric, quantity)
VALUES (...)
ON CONFLICT (tenant_id, period, metric)
DO UPDATE SET quantity = EXCLUDED.quantity, recorded_at = now();
```

Note `= EXCLUDED.quantity`, **not `+`** — the aggregate is the truth, and the row is a cache of it. **The moment that becomes `+`, the job stops being retryable again**, so it is worth a comment saying why.

> **The general form, and the fifth instance this week.** *A job that accumulates cannot be retried; a job that recomputes can.* The others were the outbox claim, the atomic chunk swap, the idempotency constraint and the queued-send revalidation — every one solved by making the operation's result depend on the world's state rather than on how many times it ran.

## 🔴 AC2 reports to Stripe, and a crash after the call bills twice

The same gap as Story 7.2's, one layer further out and with money on it. Report usage → Stripe accepts → we crash before recording that we reported → next hour reports the same period again.

**Stripe cannot be in our transaction**, so this is Story 7.2's ruling applied outward: **the idempotency key is derived from the data, not generated per attempt.**

`(tenant_id, period, metric, hour)` hashed into the Stripe idempotency key means a retry of the same hour is the *same* request to Stripe, and Stripe deduplicates it. A key generated fresh per attempt would defeat the mechanism entirely — which is the easy mistake, because generating a UUID per call looks like exactly what an idempotency key is for.

**And record the report locally after Stripe returns**, with the same derived key, so the local record is a cache of a fact Stripe already holds rather than the fact itself. If the two disagree, Stripe wins: it is the system of record for what was billed.

## AC5 and Story 7.3's limiter are two different limits with one shared rule

Story 7.3 was found to bundle three rate limits with different failure directions, and its per-tenant AI limit moved to Story 5.4 because it **must queue rather than reject**. AC5 here is a *plan* limit — messages per month — and lands in the same place for the same reason:

> **"rather than failing silently or hard-stopping ingest"**

**Ingest never stops.** A tenant over their plan limit still has their customers' mail received, threaded, and visible — because the alternative is a support team losing email over a billing state, which no plan tier should be able to cause.

What degrades is the **AI** work: drafting pauses, the conversation appears with a stated reason in the timeline, and the notice goes to owners and admins (FR56, deduplicated per condition). Same surface Story 5.4 built for the model-outage path, and the same sentence-level distinction applies — *"you are over your plan's limit"* and *"our model provider is down"* lead to different actions.

**Three stories now describe over-limit behaviour** — 5.4 (rate), 8.2 (plan), 7.3 (API). Worth stating the shared rule in one place, because it is the same rule three times: **degrade the AI, never the mail.**

## AC3's plan definition needs a home, and `tenants.plan` has no CHECK

`plan text NOT NULL DEFAULT 'trial'` with **no constraint** — noted in Story 7.3, and this is the story that owns it. Plans define seats, message limits, model tiers and feature access, so they are a small table or a checked-in config, not a free-text column.

**Config, not a table.** Plans change on a release cadence, not a business cadence; a table invites editing production pricing without a deploy, and the model allow-list (§10.4) is already code. The column gets a CHECK generated from the config, so an unknown plan cannot be written.

**Absent or unknown → the most restrictive tier**, never unlimited. Story 7.3's rule, and the same reasoning: a typo in a plan name must not create an uncapped tenant.

## AC4's downgrade is the one that loses data

Subscribe and upgrade add capability. **Downgrade removes it**, and the epic does not say what happens to what is over the new limit — more seats than the plan allows, more knowledge sources, more connected mailboxes.

**Nothing is deleted on downgrade.** Over-limit resources become read-only and are named in the UI, so a tenant who downgrades by accident can upgrade back and lose nothing. Deleting a mailbox connection because a card was declined is not a billing behaviour anyone recovers from.

**Raised for the PM:** which resources are capped, and whether over-limit ones are read-only or merely flagged. This story implements the mechanism; the policy is a product decision.
