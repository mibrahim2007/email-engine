## Story

**As a tenant,**
**I want to connect a Gmail mailbox,**
**so that my support mail flows into the product.**

## Acceptance criteria

1. OAuth flow requests read and send scopes and completes to a connected mailbox record.
2. Refresh tokens are stored encrypted and refreshed automatically before expiry.
3. `fetchSince(cursor)` returns new messages using the Gmail history id as the cursor.
4. Revoking the connection removes stored credentials and marks the mailbox inactive.
5. A revoked or expired grant sets an error state and notifies admins rather than failing silently.

---

## 🔴 Google OAuth verification is the longest lead time on this project

**AC1 requests read and send scopes.** In Gmail's API those are **restricted scopes**, and an application using them with users outside its own Google Workspace cannot go to production until Google has verified it. Verification for restricted scopes normally includes a **third-party security assessment (CASA)**, which is measured in **weeks to months** and can carry a cost.

**This is not a task in this story. It is a gate in front of the whole product** — now tracked as PRD §8 question 8.

| | |
|---|---|
| **Unverified app** | Works for accounts inside the developer's own Workspace, and for a small number of manually-added test users. Fine for building and demoing |
| **Production, external tenants** | Requires completed verification. **Epic 2 can be built and tested without it; the product cannot be sold without it** |

**What to do now, in priority order:**

1. **Start the verification application today** — like Resend's DNS records, this is one of the few items that gets shorter only by being started earlier. Unlike DNS, it is measured in weeks.
2. **Confirm the scope list is minimal.** Verification difficulty scales with how restricted the scopes are. If send can be done through the tenant's own SMTP or through Resend rather than `gmail.send`, the scope set shrinks and the assessment gets easier. **That is a product decision, not a Dev one** — raise it with the PM.
3. **Decide what ships if verification is not complete.** IMAP (Story 2.3) and the inbound webhook (Story 2.4) need no Google review, so a launch without Gmail OAuth is technically possible. Whether it is commercially viable is PRD territory.

✅ **Now PRD §8 question 8**, owned by PM + Architect, with the send-scope analysis in §8.1. The short version: **dropping `gmail.send` does not avoid verification**, because `gmail.readonly` is restricted too and reading is the product. The scope choice changes how hard the assessment is, and the only thing it costs is whether sent replies appear in the tenant's own Gmail Sent folder.

## Tasks

### Task 1 — OAuth (AC1, AC2)

- [ ] Authorisation-code flow requesting read and send scopes, completing to a `mailboxes` row via 2.1's `connect()`.
- [ ] Refresh token encrypted through 2.1's helper — **never written in plaintext, not even transiently to a log line** (2.1 AC4).
- [ ] Refresh **before expiry**, not on failure. A token that expires mid-poll turns into a silent gap in mail rather than a clean error.

### Task 2 — `fetchSince` on the history id (AC3)

- [ ] Cursor is Gmail's history id, stored in `sync_cursor` and **treated as opaque by everything above the connector** (2.1).
- [ ] **A history id can expire.** Gmail invalidates them after a period or after too much change, and the API returns an error rather than results. Handle it by falling back to a bounded date-range fetch and re-establishing the cursor — **not by fetching everything**, which on a large mailbox is an accidental backfill.
- [ ] The fallback path needs a test. It is the one branch that only fires after a mailbox has been idle, which is exactly when nobody is watching.

### Task 3 — Revoke (AC4)

- [ ] Removes stored credentials and marks the mailbox inactive.
- [ ] **Revoke at Google too**, not only locally. Deleting our copy leaves a live grant the tenant can see in their Google account and cannot explain.
- [ ] Writes an audit event via 1.5's `audit()`.

### Task 4 — Broken grants surface (AC5)

- [ ] A revoked or expired grant sets `sync_state` to an error value and **notifies admins** — in-app *and* by email, via Story 1.7. This is one of the two conditions FR56 sends email for, precisely because nobody is looking when it happens.
- [ ] **Fails loudly, never silently** (NFR23). A mailbox that stops syncing without saying so is indistinguishable from a quiet week.

## Dev notes

### The connector contract — from [Story 2.1](./2.1.md)

`connect(tenantId, provider, code)`, `refresh(mailboxId)`, `fetchSince(mailboxId, cursor)`, `send(mailboxId, outboundId)`, `revoke(mailboxId)`. Story 2.1 writes the conformance suite; **this story turns it on for `gmail`** and must not add a Gmail-shaped method to the interface.

### What this story does *not* do

Parsing, sanitisation, and attachment storage are Story 2.5. Threading is 2.6. Deduplication is 2.7. **This story hands `RawMessage` to the ingest entry point and stops** (§4.2).
