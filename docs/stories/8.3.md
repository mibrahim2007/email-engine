## Story

**As an operator, I want to see what the system is doing, so that I can fix it before customers report it.**

## Acceptance criteria

1. Structured logs carry tenant id, conversation id, and workflow run id on every entry.
2. Errors report to Sentry with tenant context and no PII in the payload.
3. Dashboards cover ingest lag, draft latency, send success rate, model cost per tenant, and error rate.
4. Alerts fire on ingest lag, send failure rate, and error rate thresholds.
5. Every user-facing error is actionable, and failed drafts appear in the conversation timeline rather than vanishing.

---

## 🔴 AC2's "no PII in the payload" is the hardest constraint in the epic, and the default behaviour violates it

This product's entire working set is personal data. Every message body is a customer's words, every `from_address` is an identifier, every draft quotes both.

**Sentry's default is to capture what it can find** — exception messages, local variables in stack frames, request bodies, breadcrumbs. An error thrown while parsing a message arrives with the message in the frame. **The failure is not a bug that needs writing; it is what happens if nobody writes the scrubber.**

**And the errors most worth reporting are the ones most likely to carry it.** A parse failure carries the MIME that failed. A draft failure carries the prompt, which contains the thread. A send failure carries the body. The correlation is exact: **the more diagnostic the error, the more personal its payload.**

**Ruling: an allow-list, not a deny-list, and a test that watches it hold.**

- **Nothing is sent by default.** The payload is built from a named set — tenant id, conversation id, message id, workflow run id, error class, stack — and everything else is dropped. A deny-list ("scrub `body_text`, `from_address`, …") fails the day someone adds a field, which is the day it matters.
- **Ids, never content.** A conversation id is enough to open the conversation in the product, where the operator is already authorised and RLS applies. **Sending the body to Sentry moves tenant data outside every control this architecture has** — it is the same reasoning §13.3 used to reject a third-party malware scanner, and it applies harder here because it would be continuous rather than per-file.
- **The test is a negative control**, and it belongs in CI: throw an error carrying a fixture message body, capture the outbound Sentry payload, and **assert the body does not appear in it.** A scrubber nobody has watched fail is decorative — this project's own repeated lesson, and this is the instance where the cost of being wrong is a disclosure rather than an outage.

`SENTRY_DSN` is already in §12's environment set, so nothing new is provisioned.

## AC1's three ids are only useful if one thing generates them

Tenant id, conversation id, workflow run id **on every entry**. The value is joining a customer report to a workflow run to a model call — and that only works if the ids are threaded through rather than logged where convenient.

Every log line comes from a context established once per request or per workflow run, not from arguments passed down by hand. **A log line missing the ids is worse than absent**, because it is the one line that will not appear when someone greps for the incident.

**And `withTenant()` already knows the tenant.** The logging context should be established beside it, so a query that runs tenant-scoped cannot log un-scoped.

## AC3's "model cost per tenant" comes free and is the one number nobody thinks to keep

§10.4: the Gateway *"reports token/cost per request, which flows into `usage_records`."* Story 8.2 records it for billing. **This dashboard is where it becomes an operational signal rather than an invoice line.**

Worth stating because the two uses diverge: billing wants a monthly total per tenant, operations wants **cost per conversation** and its distribution. A tenant whose cost per conversation triples overnight has either been attacked, misconfigured their persona, or hit a model change — and none of those show up in a monthly total until the month ends.

## AC4's thresholds are where an alert becomes noise, and the epic sets none

Three alerts named, no numbers. **An alert with a wrong threshold is worse than no alert**: it trains an operator to dismiss it, and then the real one is dismissed too.

Two of the three have a defensible source and one does not:

| Alert | Threshold from |
|---|---|
| **Ingest lag** | FR13 — 2 minutes for polled mail, 10 seconds for webhook. **Alert above the requirement, not above a guess** |
| **Send failure rate** | Story 6.1 moves a message to `dead` after 5 attempts. A rising `dead` count is the signal; a single failure is not |
| **Error rate** | Nothing. There is no requirement it maps to |

**Error rate needs a baseline before it needs a threshold**, which means it ships as a dashboard first and an alert second — after there is a week of data to say what normal is. **Shipping it as an alert on day one is choosing a number at random and calling it a control.**

**And Story 7.3's breach records land here.** That story writes them and deliberately builds no screen. The signal an operator wants is a *sustained* breach — one tenant repeatedly at their limit is a conversation about their plan, and a single 429 is the system working.

## AC5 restates NFR23, and this story does not build most of it

*"Every user-facing error is actionable, and failed drafts appear in the conversation timeline rather than vanishing."*

**That is already built, in four other stories** — 5.1 AC4 (classification failure), 5.3 (draft failure), 5.4 AC6 (model outage), 6.5 (delivery failure). Each writes a `conversation_events` row with one plain sentence.

**What this story owns is checking that the set is complete**, which nothing else does: every terminal failure state in the pipeline has a timeline sentence, and no path exits silently. That is a test walking the error taxonomy (§10.5), not a feature.

**Name what it must not rebuild:** the timeline component is Story 3.3's, the sentences belong to the stories that produce them, and the notification channel is Story 1.7's.

## NFR17 is observed here and asserted nowhere

99.9% monthly availability was reclassified on 2026-08-04 as an **operational SLO, not a testable acceptance criterion** — it is measured from production telemetry over a month, so no story can assert it.

**This story is how it is observed.** Worth stating in the story so the reclassification does not read, a year from now, as a requirement that was quietly dropped. The traceability matrix already points NFR17 here; the story should point back.

- [ ] Context established once per request and per workflow run, beside `withTenant()`.

### Task 2 — Sentry (AC2)

- [ ] **Allow-list payload construction.** Ids, error class, stack. Nothing else.
- [ ] CI negative control asserting a fixture body never reaches the payload.

### Task 3 — Dashboards (AC3)

- [ ] Ingest lag, draft latency, send success rate, error rate.
- [ ] **Model cost per conversation**, distribution — not only the monthly total.
- [ ] Story 7.3's breach records, aggregated to sustained breaches.

### Task 4 — Alerts (AC4)

- [ ] Ingest lag against **FR13's numbers**; send failures on rising `dead` count.
- [ ] **Error rate ships as a dashboard, not an alert**, until a baseline exists.

### Task 5 — Failure-surface completeness (AC5)

- [ ] A test walking §10.5's taxonomy: every terminal failure has a timeline sentence.
- [ ] **Builds no timeline and no notification channel** — those exist.
