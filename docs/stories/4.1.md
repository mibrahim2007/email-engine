## Story

**As an admin, I want to add our documentation, so that the bot answers from our content rather than guessing.**

## Acceptance criteria

1. Sources can be created as URL, uploaded file (PDF, DOCX, MD, TXT, HTML), pasted text, or FAQ pair.
2. `kb_sources` and `kb_chunks` tables exist with RLS policies and the `vector(1536)` column.
3. Sources list shows title, type, status, chunk count, and last indexed time.
4. A source can be deleted, cascading to its chunks and removing embeddings.
5. Upload validates size and type before storage and reports rejection reasons clearly.

## This story owns Epic 4's entire schema — tables, policies, and both indexes

Three documents disagreed about who builds what:

| Document | Says |
|---|---|
| PRD Epic 4, Story 4.1 AC2 | the tables and the `vector(1536)` column |
| PRD Epic 4, Story 4.4 AC1 | "semantic search uses an HNSW index" |
| Story 1.2's scope table | "`vector(1536)`, HNSW index → Epic 4, **Story 4.3**" |

Nobody was wrong; nobody owned it. **Ruling: 4.1 builds the schema in full** — both tables, both RLS policies, the `vector(1536)` column, the HNSW index, and the GIN index. Story 4.4 owns the *query* against that schema and the *tuning* of the index, which is a different act and needs real data volume to do.

`migrations/0001` created these two tables on the scratch instance with `real[]` in place of `vector(1536)` — a substitution forced by an instance this story does not use (§6.6, §6.8c). **The Drizzle schema defines the intended type.** There is nothing to revert.

```
kb_sources      id, tenant_id, type, title, uri, status, content_hash,
                last_indexed_at, created_at
kb_chunks       id, tenant_id, source_id, content, token_count, content_hash,
                embedding vector(1536), tsv (generated), metadata, created_at
```

Both indexes, from §6.3:

```sql
CREATE INDEX idx_kb_embedding ON kb_chunks
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX idx_kb_tsv ON kb_chunks USING gin (tsv);
```

**Neither leads with `tenant_id`, and neither can.** HNSW takes one vector column; GIN is unordered. §6.3's index rule does not apply — the same exemption Story 3.2 recorded for `messages.tsv`. RLS still scopes the result. **What that costs at scale is Story 4.4's problem, and it is a large one** — read that story before assuming this index works as written.

### `content_hash` is specified in three places and exists in none

FR27 requires re-index to skip "unchanged content". §8.3 says re-index "diffs by content hash so an unchanged page costs nothing". Story 4.3 AC5 says "skips chunks whose content hash is unchanged". **`content_hash` appears in no schema** — not §6.2, not `data-models.md`, not `migrations/0001`. `grep` returns nothing across the repository.

Same shape as PO finding F4: three documents describing a column, no story creating it. It gets created here, with the tables, so no later migration is needed — and it is needed at **both** levels:

| Column | Skips | Why both |
|---|---|---|
| `kb_sources.content_hash` | fetch and extraction | An unchanged URL should cost one HTTP request, not a parse |
| `kb_chunks.content_hash` | embedding | The expensive step. A one-paragraph edit re-embeds one chunk, not the document |

A source-level hash alone still re-embeds everything after a typo fix. A chunk-level hash alone still re-fetches and re-parses a 400-page PDF to discover nothing changed.

### `status` gets a CHECK, and the default is honest

`kb_sources.status` is the one status column in the schema with no CHECK — `outbound_messages.state`, `conversations.status`, and `kb_sources.type` all have one. States: `pending | extracting | embedding | indexed | error`.

`DEFAULT 'pending'` is **true here**, unlike `attachments.scan_status` (§13.3): Story 4.3's workflow really does start on insert, so a row claiming `pending` is claiming something that exists. Front-End Spec §5.4 depends on it — the row appears as `pending` before the workflow reports anything.

## ⚠ Two security gaps, both from controls written in the epic where the danger was noticed

### AC1's URL source type is a server-side request to an address the tenant chooses

§8.3's workflow begins `fetch`. Nothing in the PRD, the architecture, or the front-end spec constrains what a source URL may point at — so `http://169.254.169.254/`, `http://localhost:3000/api/…`, and an internal `10.x` address are all valid knowledge sources today.

**The architecture already holds this rule and applied it one layer over.** §13.1: `call_tenant_webhook` "requires a pre-registered URL and never accepts a model-supplied host." The reasoning is identical and the reach is worse here — the agent's webhook tool is constrained to a URL an admin registered in advance, while a KB source URL is free-form by design, since pointing at your own documentation is the feature.

What ships: fetch only `http`/`https`, resolve the host first and refuse loopback, link-local, and RFC-1918 addresses, **re-check after every redirect** (a public host that 302s to `169.254.169.254` defeats a pre-flight check), cap response size and time, and never return the response body or headers in an error message an admin can read.

### AC5's "validates size and type" is weaker than the rule for a file this product never opens

Story 2.5 and FR57 give email attachments true-type detection from magic bytes, an executable refusal at ingest, and download-only serving — hard-won after PO finding F5. §13.3 justifies not scanning them partly on this: *"It is never parsed by the AI… There is no deserialization path from a hostile file into the model."*

**That sentence is true of attachments and this story does not change it** — no attachment becomes a `kb_chunk`. But it describes the *safe* path. This story builds the other one: an uploaded PDF is fetched, handed to a parser, and its text becomes retrievable context the agent reads. **The path that gets parsed has the weaker specified control**, because FR57 was written in the epic where file handling was being examined and this upload lives in a different epic.

The asymmetry is not entirely wrong — an admin uploading their own handbook is a different threat from a stranger emailing an executable. **But AC1's URL type is not admin-authored content at all**, and it lands in the same extractor as the upload.

What ships: FR57's magic-byte true-type check and executable refusal apply to this upload path too, stated as a reuse of `packages/*`'s existing helper rather than a second implementation. Extraction runs on the size and time caps Story 4.2 sets. This does not need a new FR — it needs FR57's helper called from a second place.

**Amend §13.3** so its claim keeps the scope that makes it true: *attachments* are never parsed, and knowledge sources are a deliberately different path with its own controls. Left absolute, it reads as a property of the system and stops being one the day this story merges.

## ⚠ AC4 deletes rows that Epics 3 and 5 point at, and nothing points back

`kb_chunks.source_id` is `ON DELETE CASCADE`, so AC4's cascade works. The problem is who else holds a reference.

`drafts.citations` is `jsonb`, not a foreign key (§6.2, `data-models.md`). Front-End Spec §7 puts a citation popover on every drafted reply — *source title → chunk excerpt → retrieval score → **link to the source in `/knowledge`***. Story 5.6 AC3 shows the same chunks in the tool trace.

**Delete a source and every draft that cited it keeps a citation whose link 404s.** No constraint fires, because jsonb has no referential integrity; no error appears, because the draft is unchanged and correct. An agent auditing why the bot said something finds a dead link — on the exact surface the product offers as its answer to "can I trust this".

This is the supervision surface degrading silently, which NFR23 prohibits in the general case ("every error surfaced to a user shall be actionable").

**This story does not fix it, and must not** — `drafts` is Epic 5's table and the popover is Epic 5's component. What this story owns is **not making the situation undetectable**: soft-delete `kb_sources` with `deleted_at` and let the cascade run on hard delete at the purge window, so a citation can resolve to *"this source was removed on 3 March"* rather than to nothing.

**Raised for the PO:** Epic 5's citation rendering needs an AC for the removed-source case. Filed here rather than appended to a plausible-looking Epic 5 story, because that is how scope inflates (Story 1.2's lesson).

## Tasks

### Task 1 — Schema (AC2)

- [ ] Drizzle: `kb_sources`, `kb_chunks` per §6.2 with `content_hash` on both and the `status` CHECK.
- [ ] `embedding vector(1536)` — the intended type, never `0001`'s `real[]` substitution.
- [ ] RLS policies on both, `ENABLE` **and** `FORCE`, `USING` **and** `WITH CHECK`.
- [ ] Both indexes from §6.3.
- [ ] Story 1.3's coverage test must pass unchanged — two new `tenant_id` tables is exactly what it watches for. **Watch it fail first:** add the tables without the policies, confirm CI goes red, then add the policies.

### Task 2 — Source creation (AC1, AC5)

- [ ] Four types: URL, file, text, FAQ pair. One `kb_sources` row each; the type decides which extractor Story 4.2 runs.
- [ ] URL: scheme allow-list, host resolution and private-range refusal, re-checked after each redirect, size and time caps.
- [ ] File: FR57's magic-byte helper, executable refusal, size cap. **Call the existing helper; do not write a second one.**
- [ ] Rejections state the reason (AC5) without echoing fetched response content.
- [ ] Creation writes `status = 'pending'` and starts Story 4.3's workflow in the same request.

### Task 3 — Sources list (AC3)

- [ ] Front-End Spec §6.3: title, type icon, chunk count, last indexed, status badge, row menu.
- [ ] Chunk count is a live aggregate over `kb_chunks`, not a denormalised counter — 5,000 chunks per tenant (NFR7) does not justify a column that can drift.
- [ ] Per-source progress, never a global spinner (§5.4). Sources index independently and the list has to show that.

### Task 4 — Deletion (AC4)

- [ ] Soft delete sets `deleted_at`; the list, retrieval, and search all exclude it.
- [ ] Hard delete cascades to `kb_chunks`, which removes the embeddings — they are a column on the chunk, not a separate store.
- [ ] `audit()` inside the caller's transaction (Story 1.5's rule).
