## Story

**As an agent, I want to review and act on a draft quickly, so that reviewing is faster than writing.**

## Acceptance criteria

1. The panel shows the draft in an editable composer with confidence displayed as a number and a label, not color alone.
2. Citations are inspectable via hover-card showing the source chunk and a link.
3. Approve, edit-and-send, regenerate, and reject are single actions; `⌘Enter` sends.
4. Every outcome is recorded with the actor, the final body, and the edit distance from the original.
5. Regenerate produces a new draft with the prior one retained in history.

---

## 🔴 AC5 leaves two live drafts on one conversation, and Epic 6 sends both

**Found comparing this epic's requirements to Epic 6's design.** `drafts.state` is `proposed | approved | rejected | edited | auto_sent` (§6.2). Regenerate writes a new draft and **retains the prior one — AC5 requires it.** The prior draft was never approved and never rejected, so it stays `proposed`.

The conversation now carries **two `proposed` drafts.** Nothing in the schema says which is current: there is `created_at` and nothing else.

FR42 arms auto-send above a confidence threshold. Epic 6's drain selects drafts in `proposed` above that threshold — and **finds two.** Both were generated for the same inbound message, both are plausible, both may clear the bar.

**The customer receives two replies.**

FR41 requires each outbound message to send exactly once "even under concurrent send attempts or retries", and §8.2's `FOR UPDATE SKIP LOCKED` claim delivers that — **for one `outbound_messages` row.** This defect arrives one table upstream: two legitimate rows, each correctly sent once. Every exactly-once guarantee in the architecture is satisfied. **A uniqueness mechanism protects the table it is written on, and says nothing about a duplicate created above it.**

It is not only an auto-send problem. With auto-send off, the review panel must still decide which of two `proposed` drafts to render, and "the newest" is a convention held in query code rather than in the schema — one `ORDER BY` omitted in one repository function and an agent reviews and sends the draft they already regenerated away from.

**Ruling: superseding is a state, not an ordering.**

- Add **`superseded`** to `drafts.state`'s CHECK list. Regenerate sets the prior draft to `superseded` in the **same transaction** that inserts the replacement. AC5's "retained in history" is satisfied — the row is still there, still readable, still carries its confidence and citations.
- **A partial unique index enforces it**, so the invariant is structural rather than remembered:

```sql
CREATE UNIQUE INDEX idx_drafts_one_live
  ON drafts (tenant_id, conversation_id)
  WHERE state = 'proposed';
```

- Then two concurrent regenerates cannot both land, and Epic 6's drain cannot find two candidates, **because the database will not hold them** — not because every query remembered to sort.

Fourth time on this project the fix was to make an invariant structural rather than temporal, after the outbox's `scheduled_for`, the backfill window's `[connected_at − 30d, connected_at)`, and Story 4.3's atomic promotion.

> **A partial unique index enforces *at most one*, which is what is needed here** — and is exactly what Story 1.5's last-owner rule could not use, because that one needs *at least one*. Worth holding both cases together: the same tool, correct in one and useless in the other.

**This story owns the schema change and the transition.** Epic 6 inherits an invariant instead of a convention, and its drain needs no special case.

## AC3's four actions leave one hole

Approve, edit-and-send, regenerate, reject. **Reject with no replacement leaves the conversation with no draft and no reason** — the agent rejected it because it was wrong, and nothing records what was wrong, so Story 5.1's eval set and §1.4's "draft acceptance ≥ 70%" both count it as a rejection with no cause.

A one-tap reason on reject — *inaccurate · wrong tone · missing context · not needed* — is four buttons and is the only structured signal this product will ever get about **why** drafts fail. Everything else in the supervision surface measures what the model did; this measures what a human thought of it.

Not a new requirement: FR38 says "the outcome shall be recorded", and a rejection with no reason is a recorded outcome carrying no information.

## AC2 says hover-card, and the front-end spec already overruled it

Front-End Spec §4.2 is normative and says so: **a hover-card alone fails WCAG 2.1 AA**, hover being neither a keyboard nor a touch affordance, and NFR24 is not optional. Architecture §9.5 accepted the delta and **dropped `hover-card` entirely**.

Build §4.2: a `<button>` marker, popover on hover *and* focus, `Enter`/`Space` pins, `Esc` returns focus, bottom sheet on touch, numbered markers repeated in a footnote row so the citation set reads without any hovering at all.

**Contents, in order:** source title → chunk excerpt with the matched span emphasised → retrieval score → link to the source.

### And a fifth case §4.2 does not cover: the source is gone

Story 4.1 soft-deletes knowledge sources; Story 5.3 denormalises the excerpt onto the citation. So a citation whose source was deleted, or whose chunk a nightly re-index replaced, **still has everything the popover needs except a live link.**

Render it: title, excerpt, score, and *"This source was removed on 3 March"* in place of the link. **Raised drafting Story 4.1 and carried to here on purpose** — it is a rendering concern, and appending it to whichever story looked plausible at the time is how scope inflates.

The alternative is a popover that 404s on the surface built to answer *"can I trust this"*, which is worse than saying the source is gone.

## AC1 defers entirely to Front-End Spec §4.1

Four redundant encodings, the band table, and the threshold marker — including that it renders when auto-send is off, *especially* then, because watching drafts land above an unarmed line is what makes moving it later an informed act.

**The label is now decided** *(2026-08-07, PRD Q10 option B)*. `confidence` is computed groundedness, so the meter must say what it measures rather than imply a probability of being right: **"84% of this reply's factual sentences are backed by a source you can click."** "Confidence 87" would state something the number does not mean — groundedness is provenance, not truth (§10.4).

**And `NULL` is a fourth state the band table does not have.** A draft that makes no factual claims has no groundedness to report. It renders as *"No factual claims to check"* — not as zero, which reads as *badly* grounded and is wrong. It never auto-sends.
