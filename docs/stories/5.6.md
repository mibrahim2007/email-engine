## Story

**As an admin, I want to shape and test the bot's voice, so that I trust it before it speaks for us.**

## Acceptance criteria

1. Persona settings cover tone, formality, signature, prohibited topics, and standard disclaimers.
2. The playground streams responses using the identical agent, tools, and knowledge as production.
3. The tool-call trace is visible per response, including retrieved chunks and scores.
4. Persona changes take effect in the playground immediately without a deploy.
5. A prompt-injection corpus in the playground produces no unauthorized tool call and no data disclosure.

---

## 🔴 AC2's "identical tools" means the playground can issue a refund

FR36 and AC2 require the playground to use the **identical agent, tools, and knowledge as production**, and that requirement is right — a playground that behaves differently tests nothing, which is the whole reason it is worded that way.

But §4.6 lists `call_tenant_webhook` as *"Tenant-defined action (**order status, refund**) via signed HTTP"*, and FR49 lets an admin register an outbound action webhook the agent may call.

**So an admin typing a test message into a screen labelled "test your bot" can cause a real, signed HTTP call to their production order system.** Nothing distinguishes it from a live one — that is what "identical" delivers. A refund endpoint issues a refund; a cancel endpoint cancels an order.

**And AC5 makes it adversarial.** The prompt-injection corpus is designed to make the agent take unauthorized actions, and this story requires running it **in the playground**, one click, as a visible affordance. **The corpus that proves the bot cannot be manipulated would be firing live webhooks at the tenant's business while proving it.** AC5 asserts "no unauthorized tool call" — the assertion is about the *decision*, and by the time it can be asserted the call has already gone out.

The other two side-effecting tools are milder and real: `escalate_to_human` latches `requires_human` on a conversation that does not exist, and a notification (FR55) is raised for something nobody did.

### Ruling: identical agent, identical tools, non-dispatching sink

The difference goes **below** the agent, at the dispatcher — not in the tool list, the schemas, the prompt, or the model's view of the world:

| Layer | Playground | Production |
|---|---|---|
| Agent, prompt, persona, model | identical | identical |
| Tool definitions and schemas | identical | identical |
| Knowledge and retrieval | identical | identical |
| Read-only tools (`search_knowledge_base`, `lookup_customer`) | **execute** | execute |
| `call_tenant_webhook` | **captured, not dispatched** | dispatched |
| `escalate_to_human` | **captured, not dispatched** | dispatched |

The model decides identically, the trace records the decision identically, and AC5's assertion is made against the captured call. **AC3's trace becomes the delivery mechanism**: the playground shows the exact signed payload that *would* have gone out, to the exact registered endpoint, which is strictly more useful for testing than firing it and reading a 200.

**AC2 should be amended to say what it means**: identical agent, tools, and knowledge, with side-effecting tools captured rather than dispatched. Left as "identical", a correct implementation is a dangerous one — and this is the second time this week a requirement's absolute wording was the defect (§13.3's "no deserialization path", §10.2's "every repository function").

**Constrain it, do not document it.** The dispatcher takes an explicit mode; the tool registry marks each tool `read-only` or `side-effecting`; **a test asserts every side-effecting tool is captured in playground mode**, so a sixth tool added later cannot default to dispatching. Same reasoning as `system.ts`'s surface test and the provider-SDK lockfile assertion.

## AC4's "immediately without a deploy" is a cache-invalidation requirement wearing UI clothes

Persona lives in `tenants.settings` (jsonb). "Immediately" means the next playground message reads the current persona — so the persona must not be captured into a client-held session, a memoised server value, or a streaming context established when the chat opened.

Front-End Spec §6.2 already specifies the visible half: **a persona-changed banner when settings were edited in another tab**, because the UI must not silently serve a stale persona.

The banner is presentation. **The enforcement is that each turn re-reads the persona**, and the test is a two-tab scenario — edit in one, send in the other, assert the new persona applied. Story 1.6 AC5's lesson exactly: an AC written in UI language can quietly become the whole implementation.

## AC5 runs a corpus that §14.6 already makes non-negotiable

Testing strategy §14.6 requires the adversarial corpus in CI. **This story does not own that suite** — Story 5.2 builds the boundary and runs it. What this story owns is the **affordance**: one click in the playground, results visible.

That is worth building precisely because it is redundant. A CI suite proves the property to whoever reads CI; a button proves it to the admin deciding whether to arm auto-send. §6.2 of the front-end spec makes the point: *making the adversarial test a visible affordance rather than a CI-only artifact is what gets admins to actually look at it.*

**Name what it must not rebuild:** the corpus, the assertions, and the boundary are Story 5.2's. This story renders them.

## NFR4 — first token under 1.5s p95 — is delivered here and by nothing else

Traceability finding F11 listed NFR4 as verified by nothing, left open "until Story 5.6 exists". **It exists now.** AC2's streaming is the only place in the product where a human waits on a model in real time, which is why Front-End Spec §4.4 puts streaming here and deliberately keeps it off the draft panel.

Add it as an explicit criterion rather than leaving it implied by "streams". **F11 closes with this story**, and closing it means an assertion, not a citation — the NFR1/NFR6 lesson.
