## Story

**As a support lead, I want to automate the replies I trust, so that volume drops without risk.**

## Acceptance criteria

1. Auto-send is off by default and requires explicit enablement per tenant.
2. A configurable threshold determines which drafts send without review.
3. Auto-sent replies are clearly marked in the thread and in analytics.
4. Enabling auto-send requires acknowledging a plain-language explanation of what will happen.
5. Auto-send can be disabled instantly, and any pending auto-sends are cancelled on disable.

---

## ✅ This story's AC4 is what decided PRD §8 Q10

*Raised 2026-08-06 as a blocker; closed 2026-08-07 as option B. Kept as the record of why.*

AC2 configures a threshold on `drafts.confidence`, and **what that number was had been open since Story 5.3 was drafted** — this story is where the consequence landed: FR42 sends without human review above it.

If Q10 resolves as **A (self-report)**, this story arms an unsupervised send path on the model's opinion of its own work — and the failure is not theoretical: a fluent, wrong reply to a question the knowledge base does not cover, self-scored 0.94, sent to a customer with nobody looking, **with every supervision surface working correctly.**

If it resolves as **B (mechanical groundedness)**, AC2's threshold means *"send when this fraction of the reply's factual sentences are backed by a citation"* — a sentence a support lead can reason about, and one that Front-End Spec §5.3's backtesting dialog can honestly explain.

**AC4 is what makes this blocking rather than merely sequenced.** It requires "acknowledging a plain-language explanation of what will happen", and §5.3 specifies the dialog: *"With auto-send at 0.90, of your last 200 drafts, 84 would have sent without a person reading them."* **You cannot write that sentence's second half without knowing what 0.90 means.** Under option A the honest version is "84 drafts the model felt good about", which is an explanation that would stop most support leads from clicking the button — correctly.

**Resolved as B.** `confidence` is computed groundedness (§10.4), so AC2's threshold means *"send when this fraction of the reply's factual sentences are backed by a source the agent can click"* — and AC4's dialog can state it. **`NULL` confidence never auto-sends**, with no threshold comparison and no "treat as zero".

## AC1's "off by default" needs to be off in the schema, not in the UI

A default that lives only in the settings form is a default that a seed script, a support tool, or an API call can miss. `tenants.settings` is `jsonb` with a `'{}'` default, so **absent means off** if and only if every reader treats absent that way.

Read it once, in one place, with the absent case explicit. The alternative is a `settings.auto_send` that is `undefined` in three call sites and truthy in one.

**And "requires explicit enablement" is a role question the AC does not ask.** FR3 gives `agent` no power over tenant settings; §6.5's settings screens put persona under admin. Auto-send is the highest-consequence toggle in the product — Front-End Spec §5.3 says so outright — so it is `owner`/`admin` only, enforced in the mutation and not by hiding the toggle. **Story 1.6 AC5's lesson: the page is one typed URL away, and so is the Server Action.**

## AC5's "instantly" is two different operations and only one is instant

Disabling has to stop three things, and they are not the same act:

| | What stops it | Instant? |
|---|---|---|
| Drafts **not yet enqueued** | The enqueue check reads the setting | ✅ next draft |
| Outbound rows **`pending`** | Bulk `UPDATE … SET state='cancelled' WHERE state='pending' AND …` | ✅ |
| Outbound rows **`claimed`** | Nothing. They are mid-flight with a provider | ❌ **and this is correct** |

The third is not a gap to close. A claimed row may already be accepted by the provider, and cancelling it locally would produce exactly the ambiguity Story 6.1 AC5 exists to prevent. **The UI must say so** — "3 replies already sending cannot be recalled" — rather than reporting a clean stop that did not happen.

This is delta 3's affected-row-count principle at bulk scale: **the count is the truth, and reporting a number the user can check beats a reassurance they cannot.**

Front-End Spec §5.3: disabling is one click with no dialog, and the asymmetry is deliberate — adding risk deserves friction, removing it does not. That stays. What changes is that the resulting toast is honest about the third row.

## AC3's marking has to survive the reply leaving the product

"Clearly marked in the thread and in analytics" — `drafts.state = 'auto_sent'` covers analytics, and the conversation timeline gets a `conversation_events` row of type `auto_sent`, which §6.7's CHECK already permits.

**The thread is the harder half, and the epic does not say which thread it means.** The *product's* conversation view is straightforward. **The customer's mailbox is not marked at all**, and the tenant's own agents reading the mailbox directly — which PRD §8.1 established is exactly how a support lead audits — see a reply with no indication a human never read it.

That is not this story's to fix and it is worth recording: **Q8's "who audits" question and AC3's marking are the same question asked twice**, and whichever way Q8 lands, the auto-sent marking should follow it. Raised for the PM alongside Q8 rather than resolved here.

- [ ] `owner`/`admin` only, enforced in the mutation.

- [ ] Threshold on `drafts.confidence`, which is now computed groundedness (§10.4).
- [ ] **`NULL` never auto-sends** — no threshold comparison, no exception, no "treat as zero".

### Task 3 — The enablement dialog (AC4)

- [ ] Front-End Spec §5.3: backtest against the tenant's own last 200 drafts, live count as the slider moves, three examples with "show all".
- [ ] **The interaction is the explanation.** An abstract number is not an acknowledgement.
- [ ] Fully buildable — the number's meaning is settled (§10.4).

### Task 4 — Marking (AC3)

- [ ] `drafts.state = 'auto_sent'`; `conversation_events` row.

### Task 5 — Disable (AC5)

- [ ] One click, no dialog. Bulk-cancel `pending`; report the `claimed` count honestly.
