## Story

**As an admin,**
**I want history and continuous sync,**
**so that the product is useful the moment I connect.**

## Acceptance criteria

1. A cron runs every 2 minutes and polls all active mailboxes, respecting per-provider rate limits.
2. Connecting a mailbox starts a backfill workflow covering the previous 30 days.
3. Backfill is throttled so it never starves live ingest, and reports progress in the UI.
4. Backfilled messages are marked as historical and do not trigger drafting or notifications.
5. A mailbox failing repeatedly is backed off exponentially and flagged, not polled in a tight loop.
6. A test measures arrival-to-visible latency end to end and asserts FR13's targets — under 2 minutes for polled mail, under 10 seconds for webhook mail.

---

## 🔴 Backfill and live ingest race, and the loser is a real customer

Read AC2, AC4, and Story 2.7 AC2 together:

- Backfill covers **the previous 30 days**.
- Backfilled messages are **historical** and **do not trigger drafting**.
- Deduplication is `ON CONFLICT DO NOTHING` — **the first insert wins and the second is a silent no-op**.

A backfill of a busy mailbox takes minutes. Mail arriving *during* that window falls inside the range the backfill is still fetching. If backfill inserts it first, it is written as historical, the live path's insert is a no-op, and:

> **A customer emails support during onboarding and never gets a reply.** No error, no queue, no alert — the message is in the inbox, marked historical, and the AI never saw it.

Silent, plausible, and it happens precisely at the moment a new tenant is forming their first impression.

**Fix: bound the backfill by the connection time, not only by 30 days.**

```
backfill range = [connected_at − 30 days, connected_at)
live ingest    = [connected_at, ∞)
```

Half-open at `connected_at`, so the two ranges cannot overlap by construction rather than by timing. **Story 2.1 must decide where `connected_at` lives** — that story flags it, and this is why it matters.

**A second, smaller version of the same bug:** if backfill and the 2-minute poll both run while the cursor is being established, the poll can re-fetch what backfill is mid-way through. `ON CONFLICT` keeps the data correct, but the `historical` flag is decided by whoever inserts first. **Suppress polling for a mailbox while its backfill is running**, and let the cursor be established by the backfill's completion.

## Tasks

### Task 1 — The poll cron (AC1, AC5)

- [ ] Every 2 minutes, per `vercel.json` (§12). Reads active mailboxes via the partial index Story 2.1 creates.
- [ ] Per-provider rate limits. Gmail, Graph, and IMAP have different budgets and a shared limiter that assumes the strictest wastes the others.
- [ ] Exponential backoff on repeated failure, with the mailbox flagged (AC5). **A tight loop against a broken mailbox is how an API quota is exhausted for every tenant** — the failure is shared even though the cause is one tenant's.
- [ ] A flagged mailbox is what Story 2.2 AC5 and Story 1.7's email surface.

### Task 2 — Backfill (AC2, AC3, AC4)

- [ ] Workflow starting on connect, range **`[connected_at − 30 days, connected_at)`** per the section above.
- [ ] **Suppress the poll for that mailbox until backfill completes.**
- [ ] Throttled so it never starves live ingest (AC3). Progress reported in the UI — Front-End Spec §5.2 puts backfill behind onboarding step 3 and says it must not block, so progress is what makes non-blocking legible rather than broken.
- [ ] Historical messages skip drafting **and notifications** (AC4). A tenant connecting a mailbox must not receive 400 in-app notifications about mail from last month.

### Task 3 — Prove the latency (AC6)

- [ ] Measure **arrival to visible**, end to end. Not the cron interval, not the handler's response time.
- [ ] FR13's numbers were satisfied by construction and measured nowhere until this AC — a cron silently degrading to 4 minutes would have violated the requirement with every test green. *(Traceability finding F9.)*

## Dev notes

### Cron — [§12](../architecture/deployment.md)

```json
{ "path": "/api/cron/poll-mailboxes", "schedule": "*/2 * * * *" }
```

The 2-minute schedule is where FR13's 2-minute target comes from. **They are the same number by construction**, which is exactly why AC6 measures rather than assumes.

### What this story does not own

Dedup is 2.7. Parsing is 2.5. This story decides **which messages get fetched and when**, and hands each to the same ingest entry point.
