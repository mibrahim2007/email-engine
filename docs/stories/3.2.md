## Story

**As an agent, I want to narrow the list, so that I can work a queue instead of an ocean.**

## Acceptance criteria

1. Filters for status, assignee, mailbox, and date range combine and are reflected in the URL.
2. Free-text search covers subject, sender, and body with trigram-assisted matching.
3. Filter state survives refresh and back-navigation.
4. Saved views ("Unassigned", "Mine", "Needs human") are one click from the sidebar.
5. Search returns in under 500ms at p95 at target scale.

---

## ⚠ This story owns the migration PO finding F4 has been waiting on

**There is no full-text index on `messages` or `conversations`.** The only `tsvector` in the schema is on `kb_chunks`. `idx_msg_conv_received` supports the thread view, not search. At 50,000 conversations per tenant, AC2 as written is a sequential scan per keystroke and AC5 is unreachable.

F4 was raised in the PO gate on 2026-08-03 and its **design was settled on 08-04** once F1 ruled for Neon — but no migration was ever written, because no story owned it. **This one does.**

```sql
-- messages: full-text over subject and body, generated and indexed
ALTER TABLE messages ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (
    to_tsvector('english', coalesce(subject,'') || ' ' || coalesce(body_text,''))
  ) STORED;
CREATE INDEX idx_messages_tsv ON messages USING gin (tsv);

-- contacts: the fuzzy match §6.3 originally specified
CREATE INDEX idx_contacts_name_trgm ON contacts USING gin (name gin_trgm_ops);
```

**Both, not either.** `tsvector` handles subject and body — it is core Postgres and would have been right even on the extension-less instance. `pg_trgm` handles fuzzy *sender name* matching, which is what AC2 means by "trigram-assisted". They answer different halves of the same box.

**The index leads with nothing** — GIN indexes are unordered, so §6.3's "every index leads with `tenant_id`" does not apply here. RLS still scopes the scan; the GIN index narrows it first.
