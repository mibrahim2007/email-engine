# Story 6.1 — Outbox and exactly-once sending

| | |
|---|---|
| **Epic** | 6 — Sending and automation |

| **Drafted** | 2026-08-06, SM |
| **Delivers** | FR41, NFR18 |
| **Creates** | `outbound_messages` |
| **Depends on** | 2.1 (the connector interface), 1.4 (`system.ts`), 5.5 (`superseded`, so the drain cannot find two drafts) |

## Story

**As an operator, I want guaranteed single delivery, so that a customer never receives the same reply twice.**

## Acceptance criteria

1. `outbound_messages` records state, attempts, error, provider id, and scheduled time, with a partial index on pending rows.
2. A cron drains the outbox, claiming rows with `FOR UPDATE SKIP LOCKED` in a single statement.
3. Ten concurrent drains against 50 pending rows send each exactly once — verified by an automated test.
4. Failures back off exponentially and move to `dead` after five attempts, notifying admins.
5. A claimed row that crashes mid-send is recoverable without double-sending.

## 🔴 §8.2's claim statement runs with no tenant, and returns every column of every tenant's outbox

Two rules that were each written correctly collide in this one statement.

§8.2 gives the claim as:

```sql
UPDATE outbound_messages SET state='claimed', attempt_count = attempt_count + 1
WHERE id IN (
  SELECT id FROM outbound_messages
  WHERE state='pending' AND scheduled_for <= now()
  ORDER BY scheduled_for LIMIT 50 FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

**First: it claims nothing.** `/api/cron/drain-outbox` runs with no tenant, `outbound_messages` carries `USING (tenant_id = current_tenant_id())`, and with no tenant set the predicate is NULL and the policy denies. The drain claims **zero rows and sends nothing**, silently — the failure found across all five crons on 2026-08-05, here in the one job whose entire purpose is that replies leave the building.

**Second, and this is the new part: `RETURNING *` is a cross-tenant read of full rows.** §10.2's category-two discipline is explicit — *"identifiers only, never entity data. An enumerator that returns rows is a cross-tenant read with a job title."* `RETURNING *` hands back `last_error`, `provider_message_id`, `draft_id`, and `conversation_id` for fifty rows belonging to any tenant, onto the system connection.

### The two rules genuinely conflict, and that is why this needs a ruling rather than a patch

§10.2 says: **enumerate identifiers, then re-enter `withTenant()` to do the work.** AC2 and AC3 say: **the claim is a single atomic statement**, which is what makes exactly-once true under ten concurrent drains.

Do it §10.2's naive way — enumerate ids on the system connection, then claim inside a tenant session — and **the claim is no longer atomic with the selection.** Two drains enumerate the same pending row, both re-enter, both claim. The `SKIP LOCKED` guarantee is gone precisely because it was split.

**Ruling: the atomic claim *is* the escape hatch, with a minimal return.**

```sql
CREATE FUNCTION outbound_claim_due(p_limit int)
RETURNS TABLE (tenant_id uuid, outbound_id uuid)
LANGUAGE sql VOLATILE SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
  UPDATE outbound_messages SET state = 'claimed',
                               attempt_count = attempt_count + 1,
                               claimed_at = now()
  WHERE id IN (
    SELECT id FROM outbound_messages
    WHERE state = 'pending' AND scheduled_for <= now()
    ORDER BY scheduled_for
    LIMIT p_limit
    FOR UPDATE SKIP LOCKED
  )
  RETURNING tenant_id, id
$$;

REVOKE ALL ON FUNCTION outbound_claim_due(int) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION outbound_claim_due(int) TO email_engine_app;
```

`VOLATILE`, not `STABLE` — it writes. It is the only category-two function that does, and that is worth stating: **every other enumerator reads; this one mutates, which is what makes it atomic.** The claim and the enumeration are one act because separating them is the bug.

Two columns out. The drain then loops per tenant and re-enters `withTenant()` to read the row it was told about, fetch credentials, and send — so **everything after the claim is tenant-scoped**, and the system connection never sees message content.

**This is §10.2's `outboundClaimDue`**, which was `outboundDue` until this story was drafted. The rename is not cosmetic: a name that says "due" reads like a query and invites a future reader to call it twice, and calling this one twice claims a second batch. **It is the only category-two function that writes**, and its name should say so.

## 🔴 AC5 is not implementable behind §4.1's uniform connector interface

*"A claimed row that crashes mid-send is recoverable without double-sending."* One line, and it is the hardest requirement in the epic.

A row sitting in `claimed` after a crash is in an **unknown** state, not a failed one. The process died somewhere between the claim and the provider's acknowledgement, and nothing recorded which side of the send it was on. Two recoveries are available and both are wrong:

| Recovery | Consequence |
|---|---|
| Retry it | If the provider did accept, **the customer gets two replies** — the exact thing AC3 forbids |
| Abandon it | If the provider did not accept, the reply is silently never sent, which NFR18 forbids |

**Resolution requires asking the provider what it did**, and that is where §4.1's design becomes the obstacle: the connector exposes `send(message)` uniformly *"so the rest of the system never branches on provider"*. Recovery genuinely does branch on provider, because the three do not have the same answer.

**Ruling: generate the `Message-ID` before the attempt, and make recovery a connector capability.**

1. The composer generates the RFC 5322 `Message-ID` and **persists it on the row before the claim is released to the sender.** The identifier the provider will echo therefore exists on our side first — this is the one fact that makes any of the following possible, and it costs a column.
2. The connector interface gains `findSent(mailboxId, messageId)` alongside `send`. Recovery is: look for our own `Message-ID` in the mailbox's sent items; found → mark `sent`; not found → return to `pending`.
3. **`findSent` is not uniformly implementable, and the story says so rather than pretending.**

| Provider | `findSent` |
|---|---|
| Gmail | ✅ search `rfc822msgid:` in the sent label |
| Microsoft Graph | ✅ filter `internetMessageId` in `SentItems` |
| **IMAP/SMTP** | ⚠️ **SMTP has no such notion.** An IMAP `APPEND` to Sent is a separate operation from the SMTP send and may not have happened |
| Inbound-webhook-only | n/a — this mailbox does not send |

4. **A stale `claimed` row on an SMTP mailbox is escalated to a human, never auto-retried.** It is the one case where the honest action is to show an agent the message and ask. That is a worse outcome than automatic recovery and a much better one than guessing — and it is a real, permanent property of SMTP, not a gap to be closed later.

5. A reaper returns `claimed` rows older than a threshold to `pending` **via `findSent`**, never blindly. `claimed_at` (added above) is what makes "stale" definable.

> **§4.1's uniformity is right for `send` and wrong for recovery.** A uniform interface hides differences that do not matter; this one matters, and hiding it produces a story that reads implementable and is not. The interface gains a capability flag rather than a lie.

## AC4's exponential backoff needs a jitter and a ceiling nobody has stated

Five attempts, exponentially backed off. With a fixed base, a provider outage that fails 400 sends at once retries all 400 **at the same four moments**, which is a synchronised retry storm against a provider that is already unwell — and NFR19 wants degradation, not amplification.

Full jitter on the backoff, and a ceiling so attempt five is not scheduled days out. `scheduled_for = now() + random() * min(base * 2^attempt, ceiling)`. This is the same column the undo window and Story 6.4's delay use — **three different features, one mechanism**, which is worth keeping true.

`dead` after five notifies admins per **FR56**, which requires deduplication *per condition per mailbox* — 400 dead messages is one alert, not 400. Story 1.7 built that; this story must use it rather than sending its own mail.
