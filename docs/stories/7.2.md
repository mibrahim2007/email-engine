## Story

**As a technical admin, I want a versioned API, so that I can build against a stable contract.**

## Acceptance criteria

1. `/api/v1` implements the endpoints in the architecture's API spec.
2. Authentication accepts a bearer API key and resolves the tenant; RLS applies identically to API and UI paths.
3. Responses use cursor pagination and `application/problem+json` errors.
4. `Idempotency-Key` is honored on all POST endpoints for 24 hours.
5. An OpenAPI spec is generated and published, and integration tests exercise every endpoint.

## 🔴 AC4's idempotency and Epic 6's exactly-once are two guarantees with a gap between them

`POST /v1/conversations/:id/reply` queues an outbound reply. Two mechanisms protect it and **neither covers the join**:

| | Where it lives | What it protects |
|---|---|---|
| `Idempotency-Key`, 24h | Upstash Redis (§3, §13.1) | A retried HTTP request |
| Exactly-once send | `outbound_messages` + `FOR UPDATE SKIP LOCKED` | A row being sent twice |

The obvious implementation is: check Redis → miss → insert the outbound row → write the Redis record → return. **A crash between the insert and the Redis write leaves a queued reply with no idempotency record**, so the client's retry — which is exactly what a client does after a timeout — inserts a second one. Two legitimate outbound rows, each sent exactly once, and **the customer receives two replies.**

Redis cannot join a Postgres transaction, so no ordering of those two writes closes it. Write Redis first and a crash before the insert records an operation that never happened, which is worse: the retry is swallowed and the reply is silently never sent.

**This is the fourth instance of the same shape this week** — after the duplicate draft, the bounce loop, and the overnight queued send. It now has a checklist entry, and the entry is what caught it: *a guarantee protects the table it is written on and nothing above it; ask what selects this row later, and whether there can be two of it.*

**Ruling: for state-changing endpoints, idempotency is a Postgres constraint, not a Redis record.**

```sql
-- on the row the endpoint creates
ALTER TABLE outbound_messages ADD COLUMN idempotency_key text;
CREATE UNIQUE INDEX idx_outbound_idem ON outbound_messages (tenant_id, idempotency_key)
  WHERE idempotency_key IS NOT NULL;
```

The insert and its idempotency record become **one write that cannot half-happen**. A retry hits the unique violation, the handler catches it, looks up the existing row, and returns the original response. No window exists because there are no longer two writes.

**Redis keeps the read-side cache** — a 24-hour record of `(tenant, key) → response` so a replay is answered without touching Postgres. It is an optimisation whose loss costs latency, never correctness, which is the right job for a store that cannot participate in the transaction.

**The same applies to every POST that creates a row**: `/v1/kb/sources` gets the constraint on `kb_sources`, `/v1/mailboxes` on `mailboxes`. A POST that creates nothing durable can stay in Redis alone.

**Namespace by tenant.** `(tenant_id, idempotency_key)`, never the key alone — clients use sequential integers more often than anyone expects, and a global namespace makes one tenant's `1` collide with another's.

## ⚠ AC1 cannot be fully met in this epic, and one endpoint is worse than the rest

§7's table has eleven rows, and they are not all buildable when Epic 7 runs:

| Endpoint | Needs | Status at Epic 7 |
|---|---|---|
| `/v1/conversations*`, `/v1/messages/:id` | Epics 2, 3 | ✅ built |
| `/v1/conversations/:id/reply` | Epic 6 | ✅ built |
| `/v1/conversations/:id/draft` | Epic 5 | ✅ built |
| `/v1/kb/*` | Epic 4 | ✅ built |
| `/v1/mailboxes` | Epic 2 | ✅ built |
| `/v1/webhooks` | Story 7.4 | ✅ same epic |
| **`GET /v1/usage`** | **Epic 8's metering** | 🔴 **not built** |

`usage_records` exists as a table from `0001`. **Nothing writes to it until Story 8.2's rollup cron.** So `GET /v1/usage` would ship returning an empty array, correctly, forever — an endpoint that is live, documented in the published OpenAPI spec (AC5), passing its integration test (also AC5, because an empty list is a valid response), and **wrong**.

**Same shape as SB-1**: `users` was described by five stories as a mirror of Clerk identity and populated by none. Here the table is real, the endpoint is real, the test passes, and the data does not exist.

**Ruling: `/v1/usage` is deferred to Epic 8 and says so.** It returns `501 Not Implemented` with a `problem+json` body naming the epic, is marked absent from the OpenAPI spec rather than documented as returning nothing, and Story 8.2 owns turning it on. **A published contract that returns an honest error beats one that returns an empty truth.**

## AC2's "RLS applies identically" is the claim this epic exists to keep

The API resolves a tenant from a hashed key (Story 7.1), then must enter `withTenant()` exactly as a Server Action does. **Everything after resolution runs tenant-scoped**, and no handler holds a raw `db`.

Two API-specific ways to break it, neither of which the UI path can hit:

1. **A handler that reads before scoping.** The tenant comes from `system.ts`; the temptation is to keep using that connection for "just one more lookup". Story 1.3's ESLint rule covers it, and this story is the first consumer that will feel the rule as friction rather than as a formality.
2. **Cursor pagination that encodes a row id.** A cursor is client-supplied and comes back on the next request. If it encodes a raw `id`, a client can paste another tenant's cursor — **RLS makes that return zero rows rather than data**, which is correct, but the cursor must not be *trusted* to be this tenant's. Sign it or scope it; do not decode-and-query naively.

The second is worth stating because it is the one place a public API hands a client a database identifier and takes it back.

## AC3's `problem+json` maps to a taxonomy that already exists

§10.5 defines eight error classes with HTTP codes and retryability. `problem+json` is the wire format for exactly that table — `type`, `title`, `status`, `detail`, `instance`.

**Do not invent a second taxonomy.** The translation is mechanical and belongs in one boundary function.

**And `RateLimitError` is the one that carries a header** (`Retry-After`, Story 7.3), which is why it is worth wiring the taxonomy through rather than hand-writing responses per handler.

## AC5's "integration tests exercise every endpoint" needs a definition of exercise

An integration test that calls an endpoint and asserts `200` proves routing. The two things worth asserting on a **public** contract:

- **Every endpoint rejects a key from another tenant** — one parameterised test over the endpoint list, which is the API-layer restatement of the RLS suite and the only place it is checked through HTTP.
- **The OpenAPI spec matches the handlers.** Generate it from the route definitions rather than maintaining it alongside them; a hand-maintained spec drifts and is worse than none, because clients build against it.
