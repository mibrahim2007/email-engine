## Story

**As a tenant,**
**I want to forward mail to a webhook,**
**so that I get the product without granting mailbox access.**

## Acceptance criteria

1. `/api/webhooks/inbound` verifies the provider HMAC signature and timestamp before any parsing.
2. An unsigned, mis-signed, or stale payload is rejected with 401 and no side effects.
3. A verified payload is normalized to the same internal shape as polled messages.
4. The endpoint responds within 2 seconds by handing off to a workflow rather than processing inline.
5. The tenant is resolved from the routing address; an unknown address is rejected without creating data.

## ⚠ AC5 resolves a tenant from attacker-supplied data

The routing address arrives **in the payload**. Anyone who can reach the endpoint can propose one.

The signature check (AC1) is what makes it trustworthy — which is exactly why AC1 says *before any parsing*, and why **that ordering is the security control rather than a performance note**. Parse first and a malformed payload has already reached the MIME parser before anything established the sender was Resend.

**Order is: read raw body → verify HMAC → verify timestamp → parse → resolve tenant.** A framework that parses the body automatically before the handler runs defeats this; read the raw body deliberately.

AC5's "rejected without creating data" is the second half: an unknown routing address must not create a mailbox, a tenant, or a log line containing the full payload.

## Tasks

### Task 1 — Verify before parsing (AC1, AC2)

- [ ] Raw body, HMAC, then **timestamp tolerance** — §13.1 specifies both. Signature alone permits replay of a captured payload forever.
- [ ] Unsigned, mis-signed, and stale each get 401 with **no side effects**: no row, no workflow, no blob.
- [ ] Three separate tests. They fail differently and a single "rejects bad input" test hides which one regressed.

### Task 2 — Normalize (AC3)

- [ ] Produce the `RawMessage` **defined in Story 2.1**, identical to the pollers' output (§4.2: *"Both normalize to a `RawMessage` and enqueue one workflow run"*).
- [ ] **Everything downstream must be unable to tell which entry point a message came from.** If Story 2.5 or 2.6 needs to know, the normalisation is incomplete.

### Task 3 — Hand off, don't process (AC4)

- [ ] Respond within 2s by enqueuing the workflow. Parsing, attachment upload, and classification happen in the run, not the request.
- [ ] This is what makes FR13's 10-second webhook target achievable: the provider's timeout is satisfied by the handoff, and the work is bounded by the workflow rather than the HTTP request.
- [ ] The insert is `ON CONFLICT DO NOTHING` per Story 2.7 — **a redelivered webhook must not start a second run.** 2.7 owns that guarantee; this story calls it.

### Task 4 — Resolve the tenant (AC5)

- [ ] From the routing address, **after** verification.
- [ ] Unknown address → reject, create nothing. Rate-limit this path: it is unauthenticated by nature and an unknown-address probe is cheap to send (§13.1, per-IP on webhooks).

## Dev notes

### Order of operations — [§13.1](../architecture/security-and-performance.md)

> **Webhook verification** — Provider HMAC + timestamp tolerance **before any parsing work**.

### What this story does not do

Parsing and sanitisation are 2.5. Threading is 2.6. **Deduplication is 2.7 and is a database constraint, not a check in this handler** (§4.2: *"Deduplication is a DB constraint, not a check-then-insert"*).
