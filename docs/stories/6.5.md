# Story 6.5 — Bounce and failure handling

| | |
|---|---|
| **Epic** | 6 — Sending and automation |
| **Status** | Draft — not Approved |

| **Depends on** | 6.1 (the outbox), 2.4 and 2.5 (the ingest path a bounce arrives on), 1.7 (notifications) |

## Story

**As an agent, I want to know when a reply didn't arrive, so that I can follow up.**

## Acceptance criteria

1. Bounces and delivery failures are detected and attached to the conversation.
2. Hard bounces mark the contact address invalid and suppress further sends to it.
3. Soft bounces retry per policy before being surfaced.
4. Delivery failures are visible in the conversation timeline, not only in logs.
5. A provider outage queues sends rather than dropping or erroring them.

---

## 🔴 A bounce is an inbound email, so Epic 2 ingests it, Epic 5 classifies it, and the bot replies to `MAILER-DAEMON`

**Found comparing this epic's requirements to Epic 2's design.** AC1 says bounces are "detected" and names no mechanism, and the mechanism turns out to already exist for something else.

Most bounces arrive as a **delivery status notification** — an ordinary email, from `MAILER-DAEMON@` or `postmaster@`, sent to the mailbox that did the sending. There is no bounce API in the path for Gmail, Graph, or SMTP; the DSN *is* the notification.

So a bounce enters through Story 2.4's webhook or Story 2.8's poll, exactly like any customer message, and **nothing between the mailbox and the AI knows it is not one.** Follow it through the pipeline that already exists:

| Stage | What happens to the DSN |
|---|---|
| Story 2.5 — parse | Parses fine. It is a well-formed message |
| **Story 2.6 — thread resolution** | **Stitches it into the original conversation.** A DSN carries `In-Reply-To`/`References` for the message that failed, which is precisely what §4.3 matches on — and where subject heuristics apply, "Undelivered Mail Returned to Sender" plus the participant set lands it in the same place |
| Story 5.1 — classify | Classifies it as a customer message. Intent is nonsense, sentiment is probably negative, and `requires_human` is a coin flip |
| Story 5.3 — draft | **Generates a reply.** Grounded in the knowledge base, cited, confident |
| Story 6.3 — auto-send | Above threshold, **sends it to `MAILER-DAEMON`** |

The outcomes compound. Best case, a wasted draft and a confused agent. Worst case, **auto-send replies to a bounce, that reply bounces, and the loop runs at the drain's cadence** — a mail loop the product built out of five individually-correct stories.

And the requirement this story exists for is unmet throughout: FR44's "surface the delivery failure on the conversation" never happens, because the failure was ingested as a conversation.

**Nothing in either epic could see this.** Epic 2 has no reason to know that Epic 6 sends mail that can fail; Epic 6 assumes a detection channel that the architecture never specified. The conversation timeline (`conversation_events`) even has a **`bounced`** type in its CHECK list (§6.7) — the *record* was designed and the *detection* was not, which is the F3/F8 shape one more time.

**Ruling: bounce detection is an ingest-path classification, and it runs before Epic 5.**

1. **Story 2.5's parse step** flags a message as a DSN — `Content-Type: multipart/report; report-type=delivery-status` is the RFC 3464 marker, with sender heuristics as a fallback for the providers that do not set it cleanly.
2. **A DSN never reaches classification or drafting.** It routes here instead, so §8.1's pipeline branches once, early, on a structural property rather than on a model judgement. **This is not the classifier's job** — "is this a bounce" is answerable from a header and must not depend on a model call that can fail open.
3. **It still attaches to the conversation** (AC1) as a `conversation_events` row of type `bounced`, which is what FR44 asks for and what the CHECK list already anticipated.
4. The matching outbound row moves to `dead`, and the DSN's status code decides hard versus soft (AC2, AC3).

**This edited Story 2.5's scope**, so it was raised for the PO rather than assumed. ✅ **Approved and applied 2026-08-07 as Story 2.5 AC8** — the flag belongs with the parser that already reads the headers. Raising it first and applying it second is the Story 1.2 lesson working as intended: the change is visible in the PRD's change history rather than having appeared in a task list.

## Matching a DSN to the outbound row it is about is what `Message-ID` was persisted for

AC1's "attached to the conversation" needs to know **which send** failed, not just which conversation. A DSN embeds the original message's headers in its `message/rfc822` part — including the `Message-ID` that **Story 6.1 already generates and persists before sending**, for its crash-recovery ruling.

The same column answers both questions, which is a good sign the column is real. Without it, matching falls back to recipient plus timestamp, which is ambiguous exactly when a conversation has several outbound messages — the case that matters.

## AC2's suppression is a write nothing can undo, on evidence that can be wrong

A hard bounce suppresses further sends to an address. **A misconfigured recipient server returns 5xx for a valid mailbox**, and suppression then silently stops a real customer from ever hearing from this tenant again — with no error, because suppression working looks identical to nobody writing to them.

Three constraints, none expensive:

- **Suppression is per tenant**, on `contacts` (already tenant-scoped). One tenant's bounce says nothing about another's relationship with that address.
- **It is visible and reversible by an admin**, from the contact panel Story 3.4 built. A suppression an admin cannot see is indistinguishable from a bug.
- **It surfaces on the conversation** (AC4), so the agent who follows up learns *why* their reply is not going out — rather than composing one that is silently dropped.

**Suppression is the only irreversible-by-default write in this epic**, and §12's rule for destructive operations applies: it gets a refusal path, not just correct logic. If a single send produces suppression for more than a handful of contacts at once, that is a provider misconfiguration and not a hundred invalid addresses — stop and alert.

## AC5 is NFR19 for the send half, and Story 5.4 AC6 already built the pattern

Story 5.4 AC6 proves the *model* outage path: fail the Gateway, assert the conversation still appears with a stated reason. This is the same requirement for the *provider* outage path, and it should be tested the same way.

The distinction the timeline must carry, exactly as in 5.4: **"we could not send this yet"** and **"this could not be delivered"** are different sentences leading to different actions. A provider outage is Story 6.1's backoff doing its job; a bounce is a dead end. Collapsing them into "delivery problem" makes NFR23's "every error shall be actionable" false in the case that matters.

## Tasks

### Task 1 — DSN detection (AC1) — **Story 2.5 AC8 does the detecting**

- [ ] `multipart/report; report-type=delivery-status` flag in the parse step, sender heuristics as fallback.
- [ ] DSNs branch out of §8.1 **before** classification. Never reach drafting.

### Task 2 — Matching (AC1)

- [ ] Extract the original `Message-ID` from the DSN's `message/rfc822` part; match Story 6.1's persisted column.

### Task 3 — Classification of the failure (AC2, AC3)

- [ ] Status code decides hard versus soft. Soft retries per Story 6.1's backoff before surfacing.
- [ ] Hard → outbound `dead`, contact suppressed.

### Task 4 — Suppression (AC2)

- [ ] Per tenant, visible in the contact panel, admin-reversible.
- [ ] Refusal path on a mass-suppression event.

### Task 5 — Timeline and notification (AC4, AC5)

- [ ] `conversation_events` type `bounced` — already in §6.7's CHECK.
- [ ] Distinct sentences for "not sent yet" and "cannot be delivered".
- [ ] FR56 alert on exhausted retries, **deduplicated per condition per mailbox**.
