## Story

**As an agent,**
**I want mail parsed and made safe,**
**so that I can read a customer's message without the product becoming an attack surface.**

## Acceptance criteria

1. MIME is parsed into `body_text`, `body_html_sanitized`, and a snippet.
2. HTML is sanitized against an allow-list; scripts, event handlers, and external stylesheets are removed.
3. A documented XSS corpus produces no script execution and no external resource load.
4. Remote images are blocked by default with an explicit "show images" affordance.
5. Attachments are uploaded to Blob storage with content type, size, and checksum recorded; oversized or disallowed types are rejected with a recorded reason.
6. The stored content type is the **true type read from magic bytes**, not the claimed MIME or the extension; a mismatch is recorded and the true type wins.
7. Executable types are refused at ingest. Blob URLs are served `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`, and `scan_status` is written as `not_scanned`.

## ⚠ Storing only the sanitized HTML is a one-way door

AC1 stores `body_html_sanitized`. The original is not kept.

That is the right default — the raw HTML is attacker-controlled and storing it invites someone downstream to render it. But it has a cost worth stating: **when the sanitizer's rules improve, there is nothing to re-sanitize.** A bug that strips too much is unrecoverable, and a bypass discovered later cannot be retroactively assessed because the input is gone.

**Recommendation: keep the decision, add the evidence.** Store a hash of the raw HTML and the sanitizer's version alongside the output. That gives a later investigation something to work with, costs two columns, and does not reintroduce the raw payload.

**Escalate to the Architect if raw retention is wanted** — it is a §6 schema change and a §13.1 security posture change, not a Dev decision.

## Tasks

### Task 1 — Parse (AC1)

- [ ] `mailparser` → `body_text`, `body_html_sanitized`, snippet (§3).
- [ ] Quoted history is **stripped from the displayed body while remaining expandable** (FR17). The display half is Story 3.3; produce the data shape it needs rather than deciding the interaction here.

### Task 2 — Sanitize (AC2, AC3, AC4)

- [ ] DOMPurify against an allow-list. Scripts, event handlers, external stylesheets removed (§13.1).
- [ ] **Rendered in a sandboxed iframe with a strict CSP** — sanitisation and the CSP are two independent controls and the AC needs both. A sanitizer bypass is survivable behind a CSP; neither alone is.
- [ ] Remote images blocked by default, proxied when shown (§13.1). **Remote images are a tracking pixel by default** — the block is a privacy control, not only a security one, and the "show images" affordance should say so.
- [ ] AC3's corpus is **documented and checked in**, so it grows when a bypass is found. NFR14 does the same for prompt injection.

### Task 3 — Attachments (AC5, AC6, AC7)

- [ ] Upload to Blob with content type, size, checksum. Oversized or disallowed → rejected **with a recorded reason**, which is what makes a support conversation possible later.
- [ ] **True type from magic bytes** (AC6). `invoice.pdf.exe` must display as an executable. A mismatch between claimed and actual is itself worth recording — it is a weak signal of intent.
- [ ] `Content-Disposition: attachment` + `nosniff`, `scan_status = 'not_scanned'` (AC7). **Never `'pending'`** — that would claim a queue that does not exist (§13.3).
- [ ] Blob is a separate origin from the app, which is load-bearing: nothing an attachment contains executes in the app's origin.

## Dev notes

### Why there is no malware scan — [§13.3](../architecture/security-and-performance.md)

Deferred deliberately, and §13.1 was corrected so it no longer promises one. Every scanning option conflicted with a requirement already held: self-hosted ClamAV violates NFR25, and a third-party API forwards customers' invoices to a fourth party. **What ships is containment**, which is ACs 6 and 7. Do not add a scanner to "finish" this story.

### The AI never opens an attachment

§6.4's retrieval reads `kb_chunks`. No agent tool opens a file. That is what keeps the residual risk to "an agent chooses to download something a stranger emailed them", which their mailbox already allowed.
