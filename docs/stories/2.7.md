## Story

**As an operator,**
**I want each provider message processed exactly once,**
**so that a customer never gets two replies to one email.**

## Acceptance criteria

1. `UNIQUE (tenant_id, provider_message_id)` enforces deduplication at the database level.
2. Insert uses `ON CONFLICT DO NOTHING`; a duplicate returns success without starting a workflow.
3. Delivering the same webhook payload five times concurrently produces exactly one message row and one workflow run.
4. Poll and webhook arriving for the same message produce one row.
5. The ingest workflow is idempotent per step and resumes correctly after a simulated crash mid-pipeline.

---

## ⚠ AC2's "without starting a workflow" is the whole story

`ON CONFLICT DO NOTHING` prevents the duplicate *row*. It does not by itself prevent the duplicate *workflow* — that depends on how the insert reports what it did.

```sql
INSERT INTO messages (...) VALUES (...)
ON CONFLICT (tenant_id, provider_message_id) DO NOTHING
RETURNING id;
```

**`RETURNING` yields no row when the conflict fired.** Start the workflow only when a row comes back. Write it as insert-then-select and the race reopens: two concurrent deliveries both find no row, both insert, one conflicts — and both may still enqueue.

§4.2 says it directly: *"Deduplication is a DB constraint, not a check-then-insert."* AC3's five concurrent deliveries is the test that distinguishes the two implementations, and **it is the only test here that fails on a wrong-but-plausible version.**

## Tasks

### Task 1 — The constraint (AC1, AC2)

- [ ] `UNIQUE (tenant_id, provider_message_id)` — already in the schema.
- [ ] `ON CONFLICT DO NOTHING RETURNING id`; enqueue only on a returned row.
- [ ] **`provider_message_id` must be stable across entry points.** If the webhook and the poller derive it differently for the same mail, AC4 fails and the constraint never fires. It is part of `RawMessage`, defined in Story 2.1, not derived here.

### Task 2 — Workflow idempotency (AC5)

- [ ] Idempotency key is the message id (§8.1).
- [ ] **Every step assumes it runs at least twice** (§15.10). §8.1's checkpoints — parse, thread-resolve, classify, persist — must each be safe to repeat: the attachment upload overwrites rather than duplicates, the thread resolution is deterministic, the classification write is an upsert.
- [ ] The crash test is AC5 and needs to interrupt *between* steps, not before the run.

### Task 3 — Prove it under concurrency (AC3, AC4)

- [ ] Five concurrent deliveries of one payload → **one row, one run**.
- [ ] Poll and webhook for the same message → one row. This is the realistic case: a tenant forwarding to the webhook *and* connected over IMAP.
- [ ] Both are automated, per §14's non-negotiable list.

## Dev notes

### The pipeline — [§8.1](../architecture/core-workflows.md)

```
verify signature → INSERT (ON CONFLICT DO NOTHING) → [already exists? stop]
  → start run (idempotency: message id)
  → step: parse + sanitize + store attachments
  → step: resolve thread → conversation
  → step: classify
  → step: persist classification
```

> Each `step:` is a Workflow checkpoint. If the model call times out, **only that step retries** — the parse, the thread resolution, and the attachment uploads are not redone.

### What "exactly once" does and does not mean here

It means one row and one run per provider message. It does **not** mean one reply — the outbox (Story 6.1) owns exactly-once *sending*, with its own claim-with-`FOR UPDATE SKIP LOCKED`. **Two separate guarantees at two separate boundaries**; neither substitutes for the other, and conflating them is how a system ends up with one of each.
