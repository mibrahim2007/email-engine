## Story

**As a support lead, I want to see whether this is working, so that I can justify and tune it.**

## Acceptance criteria

1. Volume, deflection rate, draft acceptance rate, first-response time, and resolution time render over a selectable period.
2. Escalation reasons are broken down by trigger.
3. Metrics are tenant-scoped and comparable against the prior period.
4. Data can be exported as CSV.
5. Analytics queries return in under 1s at p95 at target scale.

---

## 🔴 The product's headline metric contains a term nothing can measure

AC1 names **deflection rate**, and PRD §1.4 defines it as the project's first success metric:

> Deflection rate (auto-sent, no human touch, **no follow-up complaint**) — ≥ 40% of eligible conversations

Two of those three terms are computable today. `drafts.state = 'auto_sent'` gives the first; the absence of an agent action on the conversation gives the second. **"No follow-up complaint" is not a thing the schema can express.** There is no complaint signal — no flag, no field, no event type in `conversation_events`.

So the number on the dashboard would be *auto-sent and untouched*, which is a **different and more flattering metric** than the one §1.4 commits to. It would be reported against a 40% target set for the stricter definition, and every review of it would compare the wrong quantity to the right goal.

**This is the traceability blind spot in a new place.** §1.4 is a metrics table, not a requirement, so no FR cites it and no pass compares it to the schema — and Story 5.4 hit the mirror image of this two days ago, where §1.4 held a threshold that an acceptance criterion called "agreed" and cited nowhere.

**Ruling: yesterday's classification change makes it computable, and this story should say how.**

Story 5.1 moved classification onto `messages` — every inbound message now carries its own `sentiment`, `intent` and `requires_human`. A follow-up complaint therefore has a definition the schema can support:

> An **inbound** message arriving on the conversation **after** the auto-sent reply, within a window, whose `sentiment` is negative **or** whose classification sets `requires_human`.

```
deflected = auto_sent
          AND no human action on the conversation
          AND no qualifying follow-up within N days
```

**The window is a product choice, not a technical one** — 7 days is the obvious default and it is the PM's to set, because it decides how long a conversation stays provisionally deflected. Raised rather than assumed.

> **This is the second payoff from a ruling made for another reason.** Per-message classification was ruled to stop a polite follow-up un-escalating an angry one. It also turns out to be the only thing that makes §1.4's headline metric measurable — **because "what did the customer say next" is now a stored fact rather than an overwritten one.**

## AC1's remaining metrics each need their definition written down, once

Four more numbers, and each has at least two defensible definitions. Choosing in the query and never writing it down is how two screens disagree about the same word.

| Metric | The choice that has to be made |
|---|---|
| **Volume** | Conversations, or messages? A 12-message thread is one of the first and twelve of the second |
| **Draft acceptance** | §1.4 says *"sent with no edit or minor edit"*. Story 5.5 records edit distance — **"minor" needs a threshold**, and it is a product choice |
| **First-response time** | `conversations.first_response_at` exists. Does an auto-sent reply set it? **It must**, or automation appears to make response time worse by removing the human replies that were being measured |
| **Resolution time** | `resolved_at − created_at`, and a reopened conversation (`conversation_events.reopened`) has two. Report the last, and count the reopen separately |

**Each definition ships as a comment beside the query and a line in the dashboard's own help text.** A metric whose definition lives only in SQL is one nobody can challenge, and this screen exists to be challenged — Front-End Spec §6.4: *"an analytics screen that cannot be interrogated gets distrusted and then ignored."*

## AC3's "comparable against the prior period" doubles every query, and one comparison is a lie

Two range scans per metric rather than one — acceptable. The trap is the **partial current period**: comparing eleven days of this month against thirty days of last month shows a catastrophic decline every month, on the first of the month, for every tenant.

Compare **like for like**: either equal-length windows ending now, or clearly label the current period as incomplete. The second is more honest and the first is what people expect; do both — equal-length by default, with the incomplete-period case named.

## AC5's 1s p95 is where the index rule and the aggregate meet

Five metrics, each an aggregation over a tenant's conversations, messages and drafts, doubled by AC3. At NFR7's 50,000 conversations per tenant.

`idx_conv_tenant_status_last` leads with `tenant_id` and supports the list, not a date-range aggregate. **The queries this story writes are the first in the product that scan a tenant's whole history rather than a page of it.**

Measure first, then index — but expect to add a `(tenant_id, created_at)` covering index, and **expect the escalation breakdown (AC2) to need one on `conversation_events (tenant_id, type, created_at)`**, which nothing else asks for.

**Do not reach for a materialized view yet.** It introduces a refresh cadence, a staleness window, and a second source of truth for numbers the tenant is going to argue with. If measurement says the live query cannot hold 1s, that is a finding worth recording rather than a fact to design around in advance.

## AC4's CSV export is the smallest surface in this epic with a cross-tenant risk

An export runs a query and streams a file. **It runs inside `withTenant()` like everything else**, and the filename must not be derived from user input.

The real caution: an export is the one place a tenant's data leaves the product in bulk, and it is `viewer`-visible if the nav is not checked. **`agent` and above** — the same reasoning as Story 1.6 AC5, enforced in the route, not by hiding a button.
