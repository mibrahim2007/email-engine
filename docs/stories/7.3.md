# Story 7.3 — Rate limiting

| | |
|---|---|

| **Status** | Draft — not Approved |

| **Depends on** | 7.1 (keys), 7.2 (the API surface), 2.4 (the webhook endpoint) |

## Story

**As an operator, I want request limits, so that one tenant cannot degrade the platform.**

## Acceptance criteria

1. Sliding-window limits apply per API key, per IP for webhooks, and per tenant for AI calls.
2. `X-RateLimit-Limit`, `-Remaining`, and `-Reset` headers are returned on every API response.
3. Exceeding a limit returns 429 with `Retry-After`.
4. Limits are configurable per plan.
5. Limit breaches are logged and visible to operators.

---

## 🔴 AC1 bundles three limiters with different failure modes, and one of them must not reject

They look like one requirement because they share a mechanism. They do not share a **correct response when the limit is hit**, which is the only thing that matters.

| Limiter | Triggered by | Over limit → | Owner |
|---|---|---|---|
| Per API key | A tenant's own integration | **429.** Their client, their retry, their problem to pace | This story |
| Per IP on webhooks | An unauthenticated caller at `/api/webhooks/inbound` | **Reject.** It is abuse or a misconfigured provider | This story |
| **Per tenant on AI calls** | **An inbound email arriving** | **🔴 must not reject** | **Not this story** |

**The third has no requester to return a status code to.** AI calls happen inside the workflow §8.1 starts when mail arrives — there is no HTTP client waiting, and the "caller" is a customer who emailed support. A 429 goes nowhere.

**Rejecting there violates NFR18 and NFR19.** *"No inbound message shall be lost due to a transient provider or model failure"* and *"a model provider outage shall degrade to queued drafts and human review, not to dropped mail."* A tenant hitting their AI cap and having messages dropped is precisely the outcome both forbid — and it is worse than an outage, because it happens on the tenant's busiest day.

**Ruling: the AI limiter queues; it does not reject. And it is not this story's.**

- Over cap, the classify/draft steps **defer** — the message is ingested, threaded, and visible, with the draft arriving late rather than never. Story 5.4's degraded path already built the surface for this: a conversation that appears, flagged, with a stated reason in the timeline.
- The reason sentence must distinguish *"we are at your plan's AI limit"* from *"our model provider is down"*. Different sentences, different actions — NFR23's "actionable" test, and Story 6.5 drew the same distinction for sends.
- **Ownership moves to the pipeline that consumes the budget**, alongside Story 5.4's outage path, because that is where the queueing surface already exists. ✅ **Approved and applied 2026-08-07 as Story 5.4 AC7.**

This story keeps the two limiters that face a caller. **The mechanism is shared and the failure direction is not, which is what made them look like one requirement.**

> Same shape as §12's cron question — *"ask which way a background job fails, because the same mechanism has opposite blast radii."* Here it is the same mechanism with opposite *correct responses*, and bundling them into one AC hid it.

## AC2's headers on "every API response" and AC3's 429 are cheaper to get wrong than they look

**On every response, including the 429 itself.** A client that gets a 429 with no `X-RateLimit-Reset` has to guess, and guessing means retrying too early, which is a retry storm against a limiter that is already saying stop.

`Retry-After` and `X-RateLimit-Reset` must agree. Two fields describing one instant, computed twice, is how they drift by a second and clients thrash on the boundary — compute once.

**A sliding window has no single reset instant**, unlike a fixed window. Report the moment the oldest request in the window ages out, which is when capacity actually returns. Reporting the window length instead is a lie in the direction that causes retry storms.

## AC4's per-plan limits need a floor that is not zero, and a default for a plan that has none

`tenants.plan` is `text NOT NULL DEFAULT 'trial'` with **no CHECK** — so plan names are unconstrained today, and a limiter keyed on plan will meet a value it has no entry for.

**Absent means the most restrictive configured tier, never unlimited.** A missing lookup that falls through to no limit turns a typo in a plan name into an uncapped tenant, and the failure is invisible until the bill arrives. The `attachments.scan_status` lesson: the safe default and the honest default are the same one.

**And no plan's limit is zero.** A limit of zero is indistinguishable from a broken integration from the client's side; if a plan has no API access, the key should not authenticate at all (Story 7.1's scopes), which is a 401 and a clear message rather than a 429 forever.

## AC5's "visible to operators" has no operator surface yet

Story 8.3 owns dashboards and alerts. This story writes the breach records; **it does not build a screen**, and saying so is the point of the checklist item about what a story must not rebuild.

What it owns: structured breach events carrying tenant, key prefix, limiter, and window — enough that Story 8.3 can aggregate them without re-deriving anything. **Never the key plaintext or hash** (Story 7.1 AC2).

**A breach is not an error.** It is the system working. Log it at a level that does not page anyone, and let Story 8.3 decide what a *sustained* breach means — which is the signal an operator actually wants, and a single 429 is not.

## Upstash is a network hop on the authentication path, and it can be down

The limiter runs before the handler on every request, over HTTP to Upstash (§3). **What happens when Upstash is unreachable?**

Fail **open**, and log it loudly. A limiter outage that fails closed takes the entire public API down to protect against a load problem that may not be happening — trading a certain outage for a possible one. The tenants being protected against are a minority; the tenants locked out are all of them.

This is the opposite call from `purge-blobs` in §12, and for the same reason stated there: **decide the failure direction per mechanism.** A limiter failing open risks overuse; a limiter failing closed guarantees an outage. Overuse is recoverable and billable.

- [ ] Sliding window per API key; per IP at `/api/webhooks/inbound`.
- [ ] **Not the AI limiter's behaviour** — that is Story 5.4 AC7. This story still *counts* the per-tenant AI budget; 5.4 decides what happens at the limit.

### Task 2 — Headers (AC2, AC3)

- [ ] `X-RateLimit-*` on every response including 429s.
- [ ] `Retry-After` and `-Reset` computed once, from the oldest request ageing out.

### Task 3 — Plan configuration (AC4)

- [ ] Per-plan limits; **unknown plan → most restrictive tier**, never unlimited.
- [ ] No zero limits; no API access is a scope decision, not a limit of zero.

### Task 4 — Breach records (AC5)

- [ ] Structured, no secret material, aggregatable by Story 8.3.

### Task 5 — Limiter availability

- [ ] Upstash unreachable → **fail open**, logged loudly.
