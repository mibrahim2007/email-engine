## Story

**As an admin, I want indexing to happen reliably in the background, so that adding a large document doesn't block me.**

## Acceptance criteria

1. Indexing runs as a durable workflow with per-step checkpoints.
2. Embeddings are generated in batches through the AI Gateway and written with their chunks.
3. Indexing status and progress are visible in the UI and update as the workflow proceeds.
4. A failed embedding batch retries without re-extracting or re-chunking.
5. Re-indexing skips chunks whose content hash is unchanged.

**Plus, moved here from Story 4.5 AC4 — see below:**

6. `/api/cron/reindex-kb` runs nightly, enumerates sources due for re-index across tenants, and reports what changed.

## The nightly cron moves out of the search-UI story

PRD Epic 4 puts *"nightly re-index runs on a cron and reports changes"* in **Story 4.5**, the knowledge search UI. Architecture §10.2 assigns its enumerator, `kbSourcesDueForReindex`, to **Story 4.3**. §12 declares `/api/cron/reindex-kb` and names no story at all.

So the enumerator had an owner, the cron that calls it had a different one, and the route had none — the SB-2 shape exactly, where two stories needed one thing and "whichever ships first" was left to decide.

**Ruling: the cron, its route, and its enumerator are all this story's.** Story 4.5 keeps the *on-demand* re-index trigger, which is a button in a UI and genuinely belongs there. A scheduled cross-tenant job in a search-screen story was scope, not ownership.

### `kbSourcesDueForReindex` — a category-two escape hatch

Per §10.2, the cron runs with **no tenant**, and `kb_sources` carries `USING (tenant_id = current_tenant_id())`. With no tenant set the predicate is NULL, the policy denies, and the cron enumerates **zero sources and re-indexes nothing, silently** — the same failure `poll-mailboxes` was found to have on 2026-08-05.

```sql
CREATE FUNCTION kb_sources_due_for_reindex(p_before timestamptz)
RETURNS TABLE (tenant_id uuid, source_id uuid)
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
  SELECT s.tenant_id, s.id FROM kb_sources s
  WHERE s.deleted_at IS NULL
    AND s.status IN ('indexed','empty','error')
    AND (s.last_indexed_at IS NULL OR s.last_indexed_at < p_before)
$$;

REVOKE ALL ON FUNCTION kb_sources_due_for_reindex(timestamptz) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION kb_sources_due_for_reindex(timestamptz) TO email_engine_app;
```

Two identifiers, never the row — **not** `uri`, not `title`, not `content_hash`. §10.2's first rule: an enumerator that returns rows is a cross-tenant read with a job title.

The work then re-enters `withTenant()` **per tenant**. Fetching, extracting, and writing on the system connection would bypass RLS for the whole indexing pipeline, which is the failure the design exists to prevent arriving through a scheduled job.

Add the export to `system.ts` and **extend the surface test**. `system.ts`'s permitted surface is **seven**: two bootstrap lookups plus one enumerator per cron in §12. This is one of the five enumerators, and it grows by being argued for.

## ⚠ Which way this job fails: re-index destroys, and its failure is the silent one

§12 asks this of every cron since 2026-08-05, and the answer here is not the one the schedule implies.

| Cron | Wrong enumeration means | Loud? | Reversible? |
|---|---|---|---|
| `poll-mailboxes` | no mail arrives | eventually, yes | yes |
| `purge-blobs` | attachments deleted | no | **no** |
| **`reindex-kb`** | **a tenant's knowledge is replaced with nothing** | **no** | yes, but only by re-indexing — and nobody knows to |

Re-indexing is not a read. It **replaces a source's chunks**, so it carries `purge-blobs`'s blast radius on `poll-mailboxes`'s two-minute-to-nightly cadence.

### The failure is a crash between the delete and the insert

The obvious implementation is `DELETE FROM kb_chunks WHERE source_id = $1` then insert the new set. A workflow step that dies in between — a Gateway timeout on the first embedding batch, a deploy, a function timeout on a 400-page PDF — leaves the source with **zero chunks and `status = 'indexed'`**.

That is the same terminal state Story 4.2 ruled on, arriving by a different route, and here it is worse: 4.2's version is a source that never worked, and this one is a source that **worked yesterday**. Nothing alerts. Retrieval returns fewer results, RRF still returns *something*, drafts still generate, confidence scores stay plausible. **The product does not break; it gets quietly worse**, and Epic 5's whole supervision surface is built to show what grounded a reply, not what failed to.

**Ruling: the swap is atomic, and it is the only correct shape.**

1. Embed into a **new chunk set first**, keyed by an `index_run_id`. The old chunks stay live and retrievable for the entire run.
2. When every batch has succeeded, **one transaction** deletes the old set and promotes the new one.
3. Any failure discards the new set. The source keeps its previous chunks and its previous `last_indexed_at`, and `status` returns to `indexed` — not `error`, because retrieval is unaffected. A separate `last_index_error` carries the message for AC3's UI.

**Never delete before the replacement exists.** Cost is transient double storage for one source — 5,000 chunks per tenant (NFR7) makes that trivially affordable.

4. **A refusal path, per §12's rule for destructive enumerators.** If a re-index would reduce a source from many chunks to zero, it does not promote. It keeps the old set and marks the source `empty` with the message from 4.2. A URL that has started returning a login page is the ordinary case, and it must not silently empty a knowledge base that was working.

## AC5 needs both hashes, and the source-level one saves the fetch

Story 4.1 creates `content_hash` on both tables. AC5 names only the chunk level, which alone still re-fetches and re-parses every document nightly to discover nothing changed — 500 tenants of unchanged documentation, every night, for no result.

```
fetch → hash the extracted text
  ├─ unchanged → stop. bump last_indexed_at, no extraction, no embedding
  └─ changed → chunk → per chunk:
        ├─ hash matches an existing live chunk → carry its embedding forward, do not re-embed
        └─ new or changed → embed
```

Carrying an embedding forward is a copy, not a re-embedding, which is what makes a one-paragraph edit cost one Gateway call instead of four hundred.

## Tasks

### Task 1 — The workflow (AC1, AC2, AC4)

- [ ] `workflows/index-kb-source.ts` (§10.1). Steps: fetch → extract → chunk → embed batches → promote.
- [ ] Batches of 96 (§8.3), through the Gateway. **No provider SDK** — the Gateway is the only AI dependency (§tech-stack).
- [ ] Each batch is its own checkpoint, so AC4's retry re-runs one batch and not the parse.
- [ ] Retry `RateLimitError` and `ProviderError` only (§10.5). Everything else fails the step.

### Task 2 — Atomic promotion (the ruling above)

- [ ] `index_run_id` on the new chunk set; promote in one transaction; discard on any failure.
- [ ] Refusal path when a re-index would drop a populated source to zero.

### Task 3 — Hash-based skipping (AC5)

- [ ] Source-level short-circuit before extraction; chunk-level carry-forward before embedding.

### Task 4 — Status and progress (AC3)

- [ ] `pending → extracting → embedding → indexed | empty | error`, written as the workflow proceeds.
- [ ] Per-source progress in the list (§5.4), never a global spinner.
- [ ] `last_index_error` surfaces a failed re-index **without** claiming the source is broken — its previous chunks are still serving.

### Task 5 — The cron (AC6)

- [ ] `/api/cron/reindex-kb` at `0 3 * * *`, already declared in §12.
- [ ] `kbSourcesDueForReindex` in `system.ts`, two columns, comment saying why it cannot be tenant-scoped.
- [ ] **Extend the surface test**; do not loosen it.
- [ ] Enumerate, then loop, then `withTenant()` per tenant. Never process on the system connection.
- [ ] "Reports changes" (AC6): sources re-indexed, skipped-unchanged, and refused, per run.
