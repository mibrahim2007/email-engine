## Story

**As a tenant,**
**I want to connect Microsoft 365 or a generic IMAP mailbox,**
**so that the product works regardless of who hosts my mail.**

## Acceptance criteria

1. Microsoft Graph OAuth completes and supports fetch and send with delta-token cursors.
2. IMAP connection accepts host, port, TLS mode, username, and password, and validates by connecting before saving.
3. IMAP fetch uses UIDs as the cursor and does not re-fetch previously seen messages.
4. All three providers pass the same connector conformance test suite.
5. Connection failures produce a specific, actionable error message, not a generic failure.

---

## ⚠ AC3's cursor is only valid while `UIDVALIDITY` holds

IMAP UIDs are unique **within a mailbox generation**. The server publishes a `UIDVALIDITY` value, and if it ever changes — a server migration, a mailbox recreation, some providers on rename — **every stored UID becomes meaningless**. Continue from the old cursor and you silently fetch the wrong messages or none at all.

**Store `UIDVALIDITY` alongside the UID cursor and compare on every connect.** If it changed, discard the cursor and re-establish from a bounded date range — never an unbounded refetch, which on a large mailbox is an accidental backfill.

This is the same failure shape as Gmail's expiring history id (Story 2.2 Task 2), and both belong in the conformance suite so IMAP and Gmail are proven to handle it the same way. **A cursor that can be invalidated by the server is a provider-agnostic problem**, which is the argument for testing it in the shared suite rather than per provider.

## Prerequisites

| Needed | For | Why |
|---|---|---|
| **Azure app registration** with Microsoft Graph mail permissions | AC1 | Portal action. Some Graph scopes need tenant-admin consent, which is the customer's admin, not ours |
| A **Microsoft 365 test account** | AC1, AC4 | The conformance suite needs a live mailbox |
| An **IMAP test mailbox** with known credentials | AC2–AC4 | Any provider; needs to be one whose `UIDVALIDITY` can be observed |

> Microsoft's review burden is materially lighter than Google's (Story 2.2). If Gmail verification becomes the critical path, **Graph and IMAP are the two connectors that can ship without a third-party assessment** — worth knowing when sequencing.

## Tasks

### Task 1 — Microsoft Graph (AC1)

- [ ] OAuth via Azure app registration; delta tokens as the opaque cursor.
- [ ] Delta tokens expire in their own way — handle re-establishment exactly as 2.2 does for history ids, through the shared path rather than a Graph-specific branch.

### Task 2 — IMAP (AC2, AC3)

- [ ] Accept host, port, TLS mode, username, password. **Validate by connecting before saving** (AC2) — a stored credential that has never worked is worse than a rejected form, because it fails later and looks like an outage.
- [ ] UID cursor **plus `UIDVALIDITY`**, per the section above.
- [ ] Credentials encrypted through 2.1's helper. IMAP is the one provider where we hold a reusable password rather than a revocable token — **the blast radius of a leak is larger**, which is worth stating in the connect UI.

### Task 3 — One suite, three providers (AC4)

- [ ] Turn on 2.1's conformance suite for `outlook` and `imap`.
- [ ] **The suite is the deliverable here.** If a provider needs a special case to pass it, the interface is wrong (§4.1: "so the rest of the system never branches on provider") — fix the interface rather than the test.

### Task 4 — Actionable failures (AC5)

- [ ] Distinguish and name: bad host, bad port, TLS mismatch, bad credentials, mailbox not found, server refused. **"Connection failed" is the failure this AC exists to prevent.**
- [ ] Taxonomy classes (§15.9), redacted per 2.1 AC4 — the error must name the *problem* without echoing the password.
