## Story

**As an agent,**
**I want messages grouped into conversations,**
**so that I read a thread rather than a pile of mail.**

## Acceptance criteria

1. Messages are grouped using `Message-ID`, `In-Reply-To`, and `References`.
2. When headers are missing or broken, normalized subject plus participant set within a 30-day window is used as a fallback.
3. A fixture corpus of real-world reply chains from Gmail, Outlook, Apple Mail, and mobile clients threads correctly.
4. Conversation `last_message_at` and `subject` update as messages arrive.
5. A new conversation is created when no match is found, never a wrong-thread merge.

---

## ⚠ AC5 sets the direction of every ambiguous call

"A new conversation is created when no match is found, **never a wrong-thread merge**" is not a tie-breaker — it is an asymmetry, and it should decide every judgement call in the fallback.

| Error | Cost |
|---|---|
| **Split** — one thread becomes two conversations | An agent sees a message without its context and looks slightly disorganised |
| **Merge** — two threads become one conversation | **Customer A's mail is shown inside Customer B's conversation.** With the AI enabled, a draft can quote one customer's message in a reply to another |

The second is a data-exposure incident that RLS cannot prevent, because both messages belong to the same tenant and every policy is satisfied. **Tenant isolation is not thread isolation**, and this story is the only thing standing between them.

**So AC2's fallback must be strict, not clever.** Normalized subject *and* participant set *and* the 30-day window — all three, never two of three. When in doubt, split.

---

## Tasks

### Task 1 — Header threading (AC1)

- [ ] `Message-ID`, `In-Reply-To`, `References`. `References` is the reliable one on long chains; `In-Reply-To` alone breaks when a client omits it.
- [ ] `thread_key` on `conversations`, unique per `(tenant_id, mailbox_id, thread_key)` — the constraint already exists in the schema.

### Task 2 — The fallback (AC2, AC5)

- [ ] Normalized subject — strip `Re:`, `Fwd:`, and their localised forms, collapse whitespace. **Localised prefixes are the common miss**: `AW:`, `RE:`, `TR:`, `SV:`.
- [ ] Participant set **and** a 30-day window. All three conditions, per the section above.
- [ ] **A generic subject must not merge.** "Invoice", "Question", "Hello" plus an overlapping participant set is a plausible false match — consider refusing the fallback entirely for subjects below a length or entropy floor. Splitting is the safe failure.

### Task 3 — Conversation state (AC4)

- [ ] `last_message_at` and `subject` update as messages arrive. The inbox sorts on `last_message_at` (Story 3.1), so a missed update silently buries a live thread.

### Task 4 — The corpus (AC3)

- [ ] Real-world chains from Gmail, Outlook, Apple Mail, and mobile clients. §14 lists this among the non-negotiable tests, and it is the only defence against a heuristic that works for the developer's own mail client.
- [ ] **Include adversarial cases, not just messy ones**: two different customers, same generic subject, overlapping recipients, within the window. That is the merge this story must refuse.

---

## Prerequisites

**None external.** Needs parsed headers from Story 2.5 and the `conversations` table. The fixture corpus (AC3) must be assembled from real mail — that is work, not a dependency, but it is the long pole in this story.
