## Story

**As a user,**
**I want to sign up and belong to an organization,**
**so that my team shares a workspace.**

## Acceptance criteria

1. Clerk sign-up, sign-in, and sign-out work; unauthenticated access to `(app)` routes redirects to sign-in.
2. Creating a Clerk Organization creates a corresponding `tenants` row via a verified webhook, **idempotently**.
3. `requireTenant()` resolves the tenant from the session's `org_id` and rejects a session with no active organization.
4. A user in two organizations can switch between them and the data shown changes accordingly.
5. Clerk webhook signature verification rejects unsigned or stale payloads.

---

## 🛑 The bootstrap problem — read this before AC3

`requireTenant()` calls `getTenantByClerkOrg(orgId)` **before a tenant is known**. That query is what *determines* the tenant, so it cannot run inside a tenant-scoped session.

**It is not just a naming awkwardness.** `tenants` carries `USING (id = current_tenant_id())`. With no tenant set, `current_tenant_id()` is NULL, `id = NULL` is NULL, the policy denies — so the lookup returns **zero rows and every login fails closed**. Implement AC3 naively and nobody can sign in.

**Architecture §10.2 ruled the fix on 2026-08-04:** a `SECURITY DEFINER` function, embedded below. Do not solve this by granting a role `BYPASSRLS` — that creates a credential able to read every tenant's mail to serve one lookup.

## Dev notes

### `requireTenant()` — [§10.3](../architecture/backend-architecture.md), verbatim

```ts
export async function requireTenant() {
  const { userId, orgId, orgRole } = await auth();
  if (!userId || !orgId) throw new UnauthorizedError();
  const tenant = await getTenantByClerkOrg(orgId);   // system-scoped read
  if (!tenant || tenant.status !== 'active') throw new ForbiddenError();
  return { tenant, userId, role: mapRole(orgRole) };
}
```

API-key requests resolve the tenant from the hashed key instead. **Both paths converge on the same `{ tenant, role }` shape**, so authorization is written once — do not fork it.

### The `SECURITY DEFINER` lookup — [§10.2](../architecture/backend-architecture.md)

```sql
CREATE FUNCTION tenant_by_clerk_org(p_clerk_org_id text)
RETURNS TABLE (id uuid, status text)
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
  SELECT t.id, t.status FROM tenants t WHERE t.clerk_org_id = p_clerk_org_id
$$;

REVOKE ALL ON FUNCTION tenant_by_clerk_org(text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION tenant_by_clerk_org(text) TO email_engine_app;
```

Three things that are not stylistic:

1. **It returns two columns, never the row.** Returning `tenants.*` would leak `settings` and `plan` for any `clerk_org_id` an attacker can guess.
2. **`SET search_path` is mandatory.** A `SECURITY DEFINER` function without a pinned search path is the standard PostgreSQL privilege-escalation footgun.
3. **`REVOKE FROM PUBLIC` then grant.** Functions are executable by `PUBLIC` by default.

### Identity lives in Clerk; `users` is a mirror

`users` carries no `tenant_id` and no RLS policy **by design** — a user may belong to many tenants (FR2). `rls_policy_coverage.sql` skips it by construction. Do not add a `tenant_id` to make the schema look uniform; that breaks multi-org membership, which is AC4.

`memberships` is the tenant-scoped join and *is* policed.

### Environment — [§12](../architecture/deployment.md)

`CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_WEBHOOK_SECRET`. Nothing else.
