## Story

**As a technical admin, I want scoped API keys, so that our integrations authenticate safely.**

## Acceptance criteria

1. Keys can be created with a name and scope; the plaintext value is shown exactly once.
2. Keys are stored hashed; the plaintext is never retrievable or logged.
3. Keys can be revoked immediately, and revocation takes effect on the next request.
4. Last-used time and request count are displayed per key.
5. Every key creation and revocation writes an audit event.

---

## AC1 says "scope" and `api_keys` has no scope column

```sql
api_keys  id, tenant_id, name, key_hash, key_prefix,
          last_used_at, revoked_at, created_at
```

**No scope. No role.** So as the schema stands, every key is implicitly full access to everything `/api/v1` exposes — including `POST /v1/conversations/:id/reply`, which sends mail to customers.

Third time this pattern has appeared: an acceptance criterion names a column, and `grep` finds it in no schema. `content_hash` (Epic 4) and `tenants.timezone` (Epic 6) were the others, and this one is the security-relevant instance.

**And it is worse than a missing column, because §10.3 already assumes an answer.** *"API-key requests resolve the tenant from the hashed key instead. Both paths converge on the same `{ tenant, role }` shape, so authorization logic is written once."* A key therefore **has a role** — FR3's `owner | admin | agent | viewer` — and nothing stores it.

**Ruling: `api_keys` gains `role` and `scopes`, and they are not the same thing.**

| Column | Answers | Values |
|---|---|---|
| `role` | *What may this key do?* Feeds the existing `requireRole()` so authorization stays written once | FR3's four roles |
| `scopes text[]` | *Which resources may it touch?* | `conversations:read`, `conversations:write`, `kb:read`, `kb:write`, `mailboxes:read`, `usage:read` |

Role alone is too coarse — a reporting integration wants `viewer` over conversations and nothing else, and an ingest integration wants `kb:write` and no conversation access at all. Scopes alone would duplicate the role logic §10.3 exists to avoid.

**Default is the narrowest thing that is useful, not the widest.** A key created with no scopes selected gets `conversations:read` — not everything. A default that grants send-mail because the form was submitted quickly is the `attachments.scan_status` lesson in a place where it writes to customers.

**A key can never exceed the role of the user who created it.** Enforced at creation, because otherwise an `agent` mints an `owner` key and role separation is decorative — the same escalation Story 1.6 AC5 was about, arriving through a settings form rather than a URL.

## AC3's "takes effect on the next request" is a property of a function this story does not own

`tenantByApiKeyHash` is a **bootstrap lookup** in `system.ts` (§10.2), built by Story 1.4 — because resolving a tenant from a key is the query that runs *before* a tenant exists, and `api_keys` carries `USING (tenant_id = current_tenant_id())` like every other tenant table.

So AC3 is satisfied or broken inside a `SECURITY DEFINER` function in someone else's story:

```sql
SELECT ak.tenant_id, ak.role, ak.scopes
FROM api_keys ak
WHERE ak.key_hash = p_hash
  AND ak.revoked_at IS NULL          -- AC3 lives here
```

**Without that one predicate, revocation does nothing at all** and the UI reports success. This story extends the function; it does not create it — and the extension is the return of `role` and `scopes`, which §10.2's minimal-return rule permits because they *are* the authorization decision, not entity data.

**Name what this must not rebuild:** the module, the surface test, and the escape-hatch pattern are Story 1.4's.

## 🔴 AC4's two counters are both writes on the authentication path

*"Last-used time and request count are displayed per key."* Read as a display requirement. It is two writes on **every single API request**, to one row, before any work happens.

**Both serialise.** `UPDATE api_keys SET last_used_at = now() WHERE id = $1` takes a row lock, so every concurrent request presenting the same key queues behind the previous one — and a key is *per integration*, so concurrency on one key is exactly the normal case. A request-count column is worse: it is the same lock held for the same duration with a guaranteed write every time.

Story 7.3 caps a key at some requests per window; this AC makes that window's throughput a function of one row's lock contention. **The rate limiter and the usage counter would fight over the same row**, and the API's p95 would be dominated by bookkeeping.

**Ruling: neither counter is a column written per request.**

- **`last_used_at` is throttled.** Write it only when the stored value is older than 60 seconds. "Last used" at one-minute resolution is what the UI shows anyway, and it turns a write-per-request into a write-per-minute-per-key.
- **Request count is not in Postgres.** Upstash Redis already counts every request for Story 7.3's sliding window — the number exists. Read it there and, if durable history is wanted, fold it into Epic 8's `usage_records` rollup, which is a cron that already exists.

> **The general form.** *A display requirement can be a write on the hot path.* AC4 reads like a UI feature and is the only criterion in this story that touches every request. The tell is a per-entity statistic on a high-frequency path — ask where it is written before deciding it is cheap.

## AC2's "never retrievable or logged" needs the plaintext to have one lifetime

Generate, hash, store the hash and a prefix, return the plaintext once, and **never hold it in a variable that outlives the response**. Specifically: not in the audit event (AC5), not in an error, not in a structured log field, not in a Sentry breadcrumb.

`key_prefix` exists so the UI can identify a key without it. Show `sk_live_abcd…` and the name.

Front-End Spec §6.5 already specifies the display: shown **once**, on creation, with *"an explicit 'copy now' state that cannot be dismissed accidentally"*. Build that, not a toast.

## AC5 goes inside the transaction

`audit()` on the caller's `tx` — Story 1.5's rule. A separately committed audit row can record a key creation that rolled back, and for a credential that is the audit trail claiming a key exists that does not.

Record `key_prefix`, `name`, `role`, `scopes`, actor. **Never the plaintext or the hash** — the hash is a verifier, and an append-only table nobody can delete from is the wrong place for one.

- [ ] `revoked_at`; **extend `tenantByApiKeyHash` to filter it** and to return `role` and `scopes`.

- [ ] `last_used_at` throttled to 60s resolution.
- [ ] Request count read from Story 7.3's counter. **No counter column.**

### Task 5 — Audit (AC5)

- [ ] Create and revoke, inside the transaction, no secret material.
