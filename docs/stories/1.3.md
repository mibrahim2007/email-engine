## Story

**As a security-conscious buyer,**
**I want tenant isolation enforced by the database,**
**so that an application bug cannot expose another customer's mail.**

## Acceptance criteria

1. `withTenant()` opens a transaction, sets `app.tenant_id` transaction-locally, and returns a `tx`; every repository function takes that `tx`. No raw `db` is exported outside `server/db`.
2. An ESLint `no-restricted-imports` rule fails the build on any import of `db` outside `server/db` (§15.1), **and a test proves the rule fires**.
3. No repository function contains a literal `tenant_id = ` filter (§15.2) — a lint rule or a test asserts this.
4. ⚠ RLS policy DDL lives in `packages/db/migrations/policies/` and runs **after** each Drizzle-generated migration (§6.5).
5. ⚠ `tests/rls_policy_coverage.sql` runs against the **Drizzle-migrated** schema, not only the hand-written one.
6. ⚠ The isolation suite is re-run **connected as the application role over the real connection path**, not via `SET ROLE`.

### The gap, which is the reason this story exists

RLS is currently guaranteed by hand-written SQL. From Story 1.2, **Drizzle generates the table DDL** — and a table Drizzle creates arrives with **no policy, no `FORCE`, and no `USING`/`WITH CHECK`**. Nothing in `drizzle-kit generate` knows about row-level security.

`rls_policy_coverage.sql` is the safety net and already works: it walks `pg_catalog` for anything carrying a `tenant_id` and fails on a missing forced policy. But today it runs against the schema built from `migrations/`. **Point it at the Drizzle-migrated schema and the net covers the new source of tables.** That is AC5, and it is the highest-value line in this story.

### Task 3 ⚠ — Policies survive Drizzle (AC4) — *provisional*

- [ ] `packages/db/migrations/policies/*.sql`, applied **after** each generated migration.
- [ ] **The mechanism depends on Story 1.2's `drizzle.config.ts` and db scripts.** Options, in preference order:
  1. Wrap `db:migrate` so it runs Drizzle's migrator then applies `policies/*.sql` in order — one script, no hook to forget.
  2. A separate `db:policies` step in CI after `db:migrate`. Simpler, but a developer running `migrate` alone gets an unpoliced schema.
- [ ] Whichever is chosen, **the policy files must be idempotent** — they run after every migration, not once.

### Task 4 ⚠ — Point the coverage test at the real schema (AC5) — *provisional*

- [ ] `rls_policy_coverage.sql` runs against the Drizzle-built schema. It needs no changes — it walks the catalog and does not care how the tables got there — only a job that points it at the right database.
- [ ] **Where this runs depends on Story 1.2's CI shape.** `db.yml` currently builds from `migrations/`; this is a second invocation against a Drizzle-migrated database, not a replacement. Keep both: `db.yml` proves the hand-written SQL is portable, this proves the deployed schema is correct (§6.8c).

### Task 5 ⚠ — Prove the connection path (AC6) — *provisional*

- [ ] Run `tests/rls_isolation.sql` **connected as the application role**, not as a superuser using `SET ROLE`.
- [ ] This is the open loop from 2026-08-02 that the scratch instance could never close — its app role is `NOLOGIN` with no password. Neon supplies a real credential, so the connection path becomes testable for the first time.
- [ ] **What this proves that `SET ROLE` does not:** that the role the application actually connects as is the one the policies were written for. `SET ROLE` tests the policy; connecting tests the policy *and* the credential *and* the grant path.

## Dev notes

### `withTenant()` — [§10.2](../architecture/backend-architecture.md), verbatim

> §10.2 calls this "the most important twenty lines in the codebase". Copy it; do not improve it.

```ts
// server/db/withTenant.ts
export async function withTenant<T>(
  tenantId: string,
  fn: (tx: Tx) => Promise<T>,
): Promise<T> {
  return db.transaction(async (tx) => {
    // transaction-local: cannot leak across pooled connections
    await tx.execute(sql`SELECT set_config('app.tenant_id', ${tenantId}, true)`);
    return fn(tx);
  });
}
```

**The third argument to `set_config` is the whole point.** `true` scopes the setting to the transaction. With `false`, a pooled connection carries one request's tenant into the next request — the failure mode is silent, intermittent, and cross-tenant. `tests/rls_isolation.sql` check 10 exists to catch exactly this.

### The standards these rules enforce — [§15](../architecture/coding-standards.md)

1. **Never import `db` outside `server/db`.** Repositories take a `tx` from `withTenant()`. Enforced by an ESLint `no-restricted-imports` rule.
2. **Never write a raw `tenant_id = ?` filter in a repository.** RLS does it. **A manual filter hides a missing policy** — it makes a broken policy look like working code, which is worse than the policy being obviously absent.

### What `users` looks like, and why it is not a bug

`users` carries no `tenant_id` and has no RLS policy, by design — it mirrors Clerk identity and a user may belong to many tenants. `rls_policy_coverage.sql` skips it **by construction**, because the catalog walk selects on the presence of a `tenant_id` column. Do not add one to make the schema look uniform; that would make `users` tenant-scoped and break multi-org membership (FR2).

### Retrieval queries carry no tenant predicate

§6.4's hybrid retrieval query has no `tenant_id` in it at all — RLS scopes all three scans silently. That is the intended shape everywhere, and it is what standard §15.2 protects: a developer "fixing" a query by adding `WHERE tenant_id = $1` has not made it safer, they have made a missing policy invisible.
