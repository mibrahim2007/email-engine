## Story

**As a developer, I want retrieval that handles both paraphrase and exact terms, so that product names and error codes are findable.**

## Acceptance criteria

1. Semantic search uses an HNSW index on cosine distance; keyword search uses a GIN index on `tsvector`.
2. Results are merged with Reciprocal Rank Fusion and trimmed to a token budget.
3. Results are tenant-scoped by RLS with no `tenant_id` predicate in the query.
4. Retrieval returns in under 150ms at p95 with 5,000 chunks per tenant.
5. A labeled relevance set achieves the agreed recall@8 target before Epic 5 begins.

---

## 🔴 AC3 and AC1 are individually correct and together they break semantic retrieval at target scale

**Found comparing Epic 4's requirements to Epic 1's design.** Neither pass inside Epic 4 could see it: AC1 is right about the index, AC3 is right about RLS, and §6.4's query is right about both. The defect is in what happens when they run at the scale NFR7 specifies.

### The mechanism

With an approximate index, **filtering is applied after the index is scanned.** pgvector's own documentation states it directly:

> "With approximate indexes, filtering is applied *after* the index is scanned. If a condition matches 10% of rows, with HNSW and the default `hnsw.ef_search` of 40, only 4 rows will match on average."

**An RLS policy is a filter.** `USING (tenant_id = current_tenant_id())` is applied to tuples the HNSW scan has already returned — it does not and cannot restrict which region of the graph gets searched. AC3's "no `tenant_id` predicate in the query" is exactly right for correctness and is precisely what removes any chance of the planner narrowing the scan.

Now put NFR7's numbers in:

| | |
|---|---|
| Tenants | 500 |
| Chunks per tenant | 5,000 |
| Total chunks in `kb_chunks` | **2,500,000** |
| One tenant's share | **0.2%** |
| `hnsw.ef_search` | 40 (default) |
| Expected rows surviving RLS | **40 × 0.002 = 0.08** |

§6.4's `semantic` CTE asks for `LIMIT 30`. At target scale it returns **zero rows, almost always.**

### What that looks like in production

Nothing throws. The `semantic` CTE is empty, the `keyword` CTE is not, `LEFT JOIN` and `WHERE s.id IS NOT NULL OR k.id IS NOT NULL` do exactly what they are written to do, and RRF returns a ranked list built from one input.

**Hybrid retrieval silently degrades to keyword-only search.** Every downstream consequence is invisible:

- FR29 — "combine semantic and keyword" — reads as satisfied. It runs both halves; one returns nothing.
- AC4's < 150ms **passes more easily**, because the expensive half found nothing. The performance target rewards the failure.
- Epic 5's drafts are grounded in whatever exact keyword overlap survives. A customer writing *"my card keeps getting declined"* retrieves nothing from a page titled *"Payment failures"* — which is the entire reason semantic search is in this product.
- Citations still appear, confidence is still scored, the tool trace still shows `search_knowledge_base` returning results.

**This is the failure mode the whole supervision surface cannot see, because nothing failed.**

### Why no test as specified would catch it

AC4 and AC5 both measure retrieval against **one tenant's** data. On a fixture with one tenant, that tenant is 100% of the table, RLS filters nothing, `ef_search = 40` comfortably serves `LIMIT 30`, and both criteria pass convincingly.

The defect is a *function of tenant count* and every acceptance criterion in this epic is written per tenant. **It would ship green and degrade as the product succeeded** — worse with every customer added, which is the shape that is hardest to attribute to a cause.

### Ruling

**1. Enable iterative index scans.** pgvector 0.8 — the pinned version in the tech stack — added them for this exact case: the index is scanned further until enough rows survive filtering.

```sql
SET LOCAL hnsw.iterative_scan = strict_order;
SET LOCAL hnsw.max_scan_tuples = 40000;
```

`strict_order`, not `relaxed_order`. §6.4's `semantic` CTE takes `LIMIT 30` from a distance ordering and feeds `row_number()` into RRF — relaxed order permits the wrong 30 to be taken, which corrupts the rank input the fusion is computed from. `relaxed_order` is faster and this is not the query to spend correctness on.

`SET LOCAL` inside `withTenant()`'s transaction, next to `set_config('app.tenant_id', …)`. It is transaction-local for the same reason: it must not leak across pooled connections.

**2. Raise `hnsw.ef_search` for this query.** 40 is the default for an unfiltered index. Set it per transaction alongside the above.

**3. `max_scan_tuples` is a floor on honesty, not a tuning knob.** Iterative scan is bounded — with a bound reached, the query still returns fewer rows than asked. **When the semantic CTE returns zero rows for a non-empty knowledge base, that is an observable event and must be logged**, not averaged into a latency graph. It is the only signal that distinguishes "hybrid retrieval running" from "hybrid retrieval reporting".

**4. Revisit is a partial index or partitioning, not a bigger number.** pgvector recommends partial indexes for few distinct filter values and **partitioning for many** — 500 tenants is many. Partitioning `kb_chunks` by `tenant_id` is the structural fix, and it is out of scope here: it is a schema decision affecting Epic 5's writes, and iterative scan is a `SET LOCAL` that ships today. **Recorded as the revisit trigger** — when a tenant's share of `kb_chunks` falls below the point where iterative scan hits `max_scan_tuples` routinely, partitioning stops being optional.

**5. AC4 and AC5 must be measured on a multi-tenant fixture.** At least 100 tenants of realistic volume, the tenant under test holding a normal share. **A single-tenant benchmark of this query measures a different query** — and would have certified this defect as passing.

## AC5 cannot be evaluated: its target number does not exist

*"achieves the agreed recall@8 target"* — PRD §8 **Q7** asks what that target is. It is open, owned by Architect + PM, and marked as gating Epic 4 → 5.

This is not a drafting gap; it is a genuine prerequisite. A Dev agent can build the labelled set, run the measurement, and report a number — it **cannot** decide whether that number is acceptable. Mark AC5 blocked and report the measurement rather than inventing a bar to clear.

> **Q7's answer got harder while this story was drafted.** The bar has to be set against the *multi-tenant* measurement, because the single-tenant number will be materially better and is not the one production runs. Whoever answers Q7 should be told which measurement they are setting a bar for.

§6.4's note also puts the Q7 measurement forward as the natural moment to try a Gateway reranking model against the same labelled set. That stays a footnote unless RRF misses the bar.
