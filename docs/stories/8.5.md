## Story

**As an operator, I want proof the system holds up, so that launch is not the first real test.**

## Acceptance criteria

1. A load test sustains 50 inbound messages/second with ingest draining faster than it fills.
2. Query performance is verified with 500 tenants and 50,000 conversations per tenant.
3. A nightly eval set of ~150 labeled cases per tenant archetype scores intent accuracy, citation groundedness, and escalation precision.
4. Eval regressions open an issue automatically and do not block merges.
5. Results are tracked over time so model or prompt changes are visibly attributable.

---

## This story is where Q10's deferred decision gets its evidence, and it should say so

PRD §8 Q10 closed on 2026-08-07 as **option B**: `confidence` is computed groundedness. **Option C — a second-model grader — was sequenced rather than rejected**, on the explicit condition that it becomes decidable once groundedness can be compared against human-judged correctness.

**AC3 already scores "citation groundedness".** After Q10 that is not a new measurement — it is `drafts.confidence` itself, recomputed against a labelled set. So the eval that exists to catch regressions is also the only place the Q10 follow-up can be settled, and **nothing currently says so.**

That is the failure this project has hit five times: *a decision with a settled design and no owner never gets built*. Q10's ruling says "if the two diverge, C becomes a decision with evidence" — **and evidence has to be somebody's acceptance criterion.**

**Ruling: AC3 scores three quantities per case and reports the correlation between two of them.**

| Scored | From |
|---|---|
| Intent accuracy | Story 5.1's labelled set (PRD Q9's bar) |
| Escalation precision **and recall** | Story 5.4, §1.4's ≥ 85% precision |
| **Groundedness** (`confidence`) | Story 5.3's computation |
| **Human-judged correctness** | **The label — this is the new part** |

The labelled case already needs an "acceptable reply traits" field (§14.7). Correctness is that field applied as a verdict, and **the report is the correlation between computed groundedness and human correctness.** High correlation means B is doing its job and C is unnecessary. Low correlation is the evidence that buys C.

**`model_confidence` is scored alongside, unused by any gate**, exactly as the Q10 ruling intends: the gap between claimed and computed is the leading indicator of a model regression, and this is the run that would see it first.

## AC1 and AC2 need environments, not code, and they are not the same environment

| | Needs | Why it cannot be local |
|---|---|---|
| **AC1** — 50 msg/sec sustained | A deployed preview against a real Neon branch, real Workflow runs, real Gateway calls | Ingest draining "faster than it fills" is a property of **queue behaviour under concurrency**, and a laptop measures a laptop |
| **AC2** — 500 tenants × 50k conversations | A **seeded database**, 25 million conversation rows | Query plans change with table size; the planner picks differently at 25M rows than at 25k |

**AC1 costs money to run** — Gateway calls at 50/second, for long enough to be a sustained test, on real models. That is a prerequisite, not a task, and worth saying before someone runs it once by accident.

**AC1 should be run with the AI steps stubbed first.** The claim is about *ingest* draining — parse, thread, persist, enqueue — and NFR8 is about the queue, not the model. Establish that ingest holds at 50/second with a stubbed classifier, **then** run the full path at a lower rate to price it. Two cheaper tests that answer different questions beat one expensive test that answers neither cleanly.

## AC4's "do not block merges" is deliberate and easy to erode

§14 is explicit: the nightly eval *"runs nightly, not per-PR; a regression opens an issue, it does not block the merge."* The RLS suites and the injection corpus block; this does not.

**The reason is worth restating in the story**, because the first time an eval regression ships a visible quality drop, the instinct is to make it blocking:

- Eval scores are **noisy** — a model provider's silent update moves them without any change on our side.
- A blocking gate on a noisy signal gets **waived**, and a gate that is routinely waived is worse than none, because it teaches the team that a red check is normal.
- The eval's job is **attribution over time** (AC5), not admission control.

**§12 also notes it is not a Vercel cron** — it runs on a CI schedule, has no tenant to establish, and touches no tenant data. *"Listing it there would give it a scoping problem it does not have."*

## AC5's attribution needs the inputs recorded, or the trend is uninterpretable

*"Model or prompt changes are visibly attributable."* A score over time is only attributable if every run records **what produced it**: model id, prompt version, retrieval config (including §6.8f's `hnsw.*` settings), corpus version, and the commit.

**Without those the chart shows that something changed and not what** — and the most common cause is the one we do not control, a provider updating a model behind a stable name. Recording the model id is not enough on its own; recording the *date* alongside it is what lets a silent update be inferred later.

**Retrieval config matters more than it looks.** §6.8f's iterative-scan settings change what the retriever returns, so a groundedness score moves when they are tuned — and tuning them is explicitly expected once there is real volume. A run that does not record them produces a regression nobody can attribute.
