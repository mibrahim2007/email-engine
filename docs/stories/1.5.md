## Story

**As an owner,**
**I want to invite teammates with roles,**
**so that access matches responsibility.**

## Acceptance criteria

1. Roles `owner`, `admin`, `agent`, `viewer` stored on membership, mapped from Clerk organization roles.
2. `requireRole()` guards every mutation; a `viewer` receives 403 on any write.
3. Owners and admins can invite by email, remove members, and change roles from the Team settings screen.
4. **The last remaining `owner` cannot be removed or demoted.**
5. **This story owns the audit write path** — a single `audit(actor, action, entity, metadata)` helper that every later state change calls. Membership changes are its first caller.
6. A test asserts the application role cannot `UPDATE` or `DELETE` `audit_events` (NFR15).

---

## ⚠ AC4 is a concurrency problem, not a validation rule

"The last remaining owner cannot be removed or demoted" reads like an `if`. Implemented as one, it is wrong:

```
Admin A: SELECT count(*) WHERE role='owner'  → 2   ✓ safe to demote Bob
Admin B: SELECT count(*) WHERE role='owner'  → 2   ✓ safe to demote Alice
Admin A: UPDATE ... Bob   → agent
Admin B: UPDATE ... Alice → agent
                                              → 0 owners. Tenant is unadministrable.
```

Classic time-of-check to time-of-use. Both requests were individually valid; together they are not. **A tenant with zero owners cannot invite, re-role, or manage billing — it needs support intervention to recover**, which makes this a data-integrity bug rather than a UX one.

**Fix: serialise membership mutations per tenant.** Take a row lock on the tenant at the top of the transaction:

```sql
SELECT id FROM tenants WHERE id = current_tenant_id() FOR UPDATE;
```

Every membership write then queues behind it, so the count is read under the lock and cannot go stale. Membership changes are rare — a lock here costs nothing.

A deferred constraint trigger checking the owner count at `COMMIT` is the more elegant alternative and harder to get right, since it must fire on `UPDATE` and `DELETE` and cope with the tenant itself being deleted. **Take the lock; note the trigger in the Dev record if you try it.**

> **A unique index cannot express this.** Constraints enforce "at most one", never "at least one" — there is no row to hang the constraint on when the last one leaves.

## Dev notes

### `requireTenant()` returns what `requireRole()` builds on — [§10.3](../architecture/backend-architecture.md)

```ts
return { tenant, userId, role: mapRole(orgRole) };
```

Both the session path and the API-key path converge on `{ tenant, role }`, **so authorization is written once**. `requireRole()` must work identically for an API key (Epic 7) — do not reach for Clerk inside it.

### Standards that bite here — [§15](../architecture/coding-standards.md)

- **§15.8** — every mutation calls `requireRole()` before touching data.
- **§15.9** — errors are taxonomy classes, never strings or bare `Error`.
- **§15.2** — no literal `tenant_id =` filter. `memberships` is tenant-scoped and RLS handles it; the owner-count query needs no tenant predicate.

### `users` vs `memberships`

`users` is a global mirror of Clerk identity with no `tenant_id` and no RLS. `memberships` is the tenant-scoped join and **is** policed. Role lives on the membership, never on the user — a user is an `owner` in one tenant and a `viewer` in another (FR2).
