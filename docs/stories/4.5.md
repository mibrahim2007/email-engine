## Story

**As an admin, I want to search the knowledge base myself, so that I can tell whether the bot will find the right answer.**

## Acceptance criteria

1. A search box returns ranked chunks with content preview, source, and score.
2. Each result links to its source and shows why it matched (semantic, keyword, or both).
3. Zero-result queries suggest what to add.
4. ~~Nightly re-index runs on a cron and reports changes.~~ **Moved to Story 4.3 AC6** — the cron, its route, and its enumerator now share one owner. See below.
5. Admins can trigger re-index of a single source on demand.

---

## AC4 moved out; AC5 stayed

Architecture §10.2 assigns `kbSourcesDueForReindex` to Story 4.3. §12 declares `/api/cron/reindex-kb` and names no story. AC4 put the schedule here. **Three documents, three owners, one job.**

A scheduled cross-tenant job needing a `SECURITY DEFINER` escape hatch is not a search-screen concern, and splitting it from its enumerator is the SB-2 shape — the failure mode being that whichever story ships second finds the piece it needs half-built and does the cheap thing.

**AC5 is genuinely this story's**: a row-menu button on a screen this story owns, calling a workflow Story 4.3 built. The trigger is UI; the job is not.

---

## AC2 is the reason this screen exists, and it comes free from §6.4

*"Why it matched"* is not a new computation. §6.4's fusion already `LEFT JOIN`s both candidate sets, so each result carries the answer:

| `s.id` | `k.id` | Matched |
|---|---|---|
| not null | null | semantic |
| null | not null | keyword |
| not null | not null | both |

Surface it directly. Front-End Spec §6.3 says direct search "is also how an admin debugs a bad citation" — and *which half found it* is the debugging information. A chunk that only ever matches on keyword is a chunk whose embedding is not doing its job.

**This screen is the only place in the product where a human sees the two halves separately**, which makes it the one surface where Story 4.4's silent degradation becomes visible to someone who is not reading logs. Worth building for that reason alone: if the semantic half stops returning anything, an admin using this screen sees every result labelled `keyword` and can say so.

Show the score to three decimal places, not a bar or a percentage. RRF scores are small and close together — `0.0328` versus `0.0164` is the difference between rank 1 and rank 30, and a progress bar makes both look full.

## AC3's "suggest what to add" needs a bounded meaning

Left as written this becomes a chat feature. **It is the empty state, and Story 3.1 AC4's rule applies** — empty states are designed, not default.

Zero results means one of three things, each with a different next step:

| Cause | What the screen says |
|---|---|
| No sources indexed at all | Point at "add a source". This is onboarding, not search |
| Sources exist, query matched nothing | Show the query, offer to add it as an FAQ pair — the shortest path from a gap to a fix |
| Sources exist but all are `empty` or `error` | **Say that.** The knowledge base has rows and no content |

The third case is where Stories 4.2 and 4.3 pay off. A tenant whose only source is a scanned PDF gets `empty`, and this screen is where they find out that "no results" is not about the query.

## Tasks

### Task 1 — Search (AC1, AC2)

- [ ] Calls Story 4.4's `retriever`. **Does not reimplement the query** — a second copy of §6.4 is a second place to forget `SET LOCAL hnsw.iterative_scan`.
- [ ] Chunk preview with the matched span emphasised, source title linking to `/knowledge/[sourceId]`, RRF score to 3dp, match-type badge.
- [ ] Server Component with the search term in the URL, so a result set is linkable — the same reasoning as Story 3.2's filters.

### Task 2 — Empty states (AC3)

- [ ] The three cases above, distinguished by source counts and statuses, not by one generic message.

### Task 3 — On-demand re-index (AC5)

- [ ] Row-menu action on the sources list, starting Story 4.3's workflow for one source.
- [ ] Disabled while that source is mid-index. **Two concurrent runs on one source is a race**, not a UI annoyance: both build a chunk set and both try to promote, so the loser's chunks leak. Story 4.3's promotion transaction should hold a source-level lock; this story must not rely on the button being disabled as the enforcement. Hiding the control is presentation — the guard is in the workflow.

### Task 4 — Source detail (§6.3)

- [ ] Chunks with token counts, heading path, and index run.
