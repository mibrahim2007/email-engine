## Story

**As an agent, I want incoming mail categorized, so that I can prioritize and the system can route.**

## Acceptance criteria

1. Every inbound message is classified into intent, sentiment, urgency, language, PII detected, and requires-human.
2. Classification uses structured output with a validated schema and runs on a fast model tier.
3. Results are persisted on the conversation and shown as badges in the inbox.
4. Classification failure marks the message for human handling rather than blocking the pipeline.
5. Accuracy against a labeled set meets the agreed threshold before drafting is enabled.

---

## 🔴 AC1 classifies a message and AC3 stores it on the conversation, so the fifth message erases the first four

FR30 and AC1 are per **message**. AC3 persists per **conversation**. `conversations` carries exactly one `intent`, one `sentiment`, one `urgency`, one `requires_human` (§6.2), and `messages` carries none of them.

So each inbound message overwrites its predecessor's classification. For a single-message conversation the two levels are identical — **which is every conversation in testing**, and the reason this reads as fine.

It is not fine, and the worst consequence is not the lost history.

### `requires_human` is a latch that a later classification silently releases

Story 5.4 AC1 escalates on strong negative sentiment. Take the ordinary sequence:

| | Message | Classification writes |
|---|---|---|
| 1 | "How do I export my invoices?" | `intent=billing`, `requires_human=false` |
| 2 | "Still waiting. This is the third time." | `sentiment=negative`, **`requires_human=true`** — escalated, flagged, sorted up (5.4 AC2) |
| 3 | "Never mind, found it. Thanks!" | `sentiment=positive`, **`requires_human=false`** |

**Message 3's classification un-escalates the conversation.** It drops out of the escalation queue, off the top of the list, and the notification FR55 raised now points at a conversation with no flag on it. **Nobody ever read message 2**, and there is no record that anybody was supposed to.

The failure is silent, it is worse the more polite the customer is, and §1.4's "escalation precision ≥ 85%" measures flags that were *raised* — it cannot see one that was withdrawn.

**Ruling: escalation is a latch, not a classification.**

`requires_human` is set by classification and **cleared only by a human action** — an agent resolving, assigning, or explicitly dismissing the flag. A classifier may raise it and may never lower it. This is the same shape as Story 1.5's last-owner rule and the send-undo race: **an acceptance criterion that reads like a field is a state machine.**

### And the classification itself belongs on the message

Store the full classification on `messages` — that is what FR30 says and what the analytics in FR50 need — and keep the conversation's columns as a **derived summary** of its messages, with explicit rules rather than last-write-wins:

| Conversation column | Derived as |
|---|---|
| `intent` | the **first** classified intent — what the customer originally wanted, which is what an intent breakdown is asking |
| `sentiment` | the **most negative** seen, not the latest |
| `urgency` | the **maximum** seen |
| `requires_human` | latched true; cleared only by a human |

**Schema addition owned by this story:** `messages` gains `intent`, `sentiment`, `urgency`, `language`, `pii_detected`, `requires_human`, `classified_at`, and `classification_model`. Drizzle, no hand-written migration — `messages` on Neon is defined by Story 1.2's successors, and Epic 2 writes rows there before this story runs, so the columns are nullable and backfilled by nothing. A message that predates this story is `classified_at IS NULL`, which is true and distinguishable from "classified as nothing".

---

## AC4's "rather than blocking the pipeline" needs the timeline, not just the flag

Setting `requires_human` on a classification failure is right and invisible. NFR23 prohibits silent AI failures — *"a failed draft shall appear in the conversation timeline"* — and a failed **classification** is upstream of the draft, so it fails the same requirement one step earlier.

Write a `conversation_events` row of type `draft_failed` (§6.7's CHECK list already permits it) with the one plain sentence Story 5.4 AC3 asks for: *"Automatic classification failed, so this was sent for human review."* The agent then knows why a conversation with no badges and no draft is sitting in their queue, instead of assuming the product ignored it.

Per §10.5, only `RateLimitError` and `ProviderError` retry. Everything else fails the step immediately and lands here.

---

## AC5 has no number, and unlike Epic 4's the gap is not recorded anywhere

*"meets the agreed threshold"*. PRD §1.4 sets **draft acceptance ≥ 70%** and **escalation precision ≥ 85%** — so Story 5.4 AC5's threshold does exist and merely needs citing. **Classification accuracy has no target in any document**, and no open question asks for one.

This is not the same as Q7, which is open and owned. This one is *absent* — the epic says "agreed" about something nobody has been asked to agree.

**Raised as a new PRD open question (Q9), owner PM + Architect**, and it needs to be answered per field rather than as one number: intent accuracy over a dozen classes, a boolean `requires_human`, and an ordinal urgency are three different measurements, and **`requires_human` recall matters far more than intent accuracy** — a missed escalation reaches a customer, a wrong intent label sorts a list wrongly.

Mark AC5 blocked. Build the labelled set, report per-field figures, do not invent a bar.
