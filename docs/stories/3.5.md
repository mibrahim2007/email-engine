## Story

**As an agent, I want to write and send a reply myself, so that I am never blocked by the AI.**

## Acceptance criteria

1. A composer supports plain text with basic formatting and renders both HTML and text parts.
2. The reply threads correctly into the customer's existing thread.
3. The tenant signature is appended and previewable.
4. Send is disabled while in flight and shows an unambiguous result.
5. A sent reply appears in the thread immediately and sets `first_response_at` if unset.

---

## 🔴 This story sends mail, and every guarantee about sending lives in Epic 6

Epic 3's stated goal is that **"a support team could use the product today with zero AI"**. That is only true if replies actually go out. But:

| Guarantee | Requirement | Where it is built |
|---|---|---|
| Exactly-once sending | FR41 | **Story 6.1** — outbox, `FOR UPDATE SKIP LOCKED` |
| Correct threading headers | FR39 | **Story 6.2** |
| Signature and branding | FR40 | **Story 6.2** |
| Bounce and failure surfacing | FR44 | **Story 6.5** |

**Three of this story's five ACs restate Epic 6 requirements.** AC2 is FR39. AC3 is FR40. And AC4's "unambiguous result" is unachievable without FR44's failure detection — a send that silently bounces is not an unambiguous result, it is a lie told confidently.

**Implemented naively — the connector's `send()` called straight from a Server Action — this ships a reply path with no retry, no exactly-once claim, and no bounce handling.** §14 lists send-exactly-once as a **merge blocker**, so that implementation cannot pass review regardless.

### Recommendation to the PO

**Story 3.5 enqueues to `outbound_messages`; it does not send.** The table exists (`0001`, `0003`) and §8.2 defines the drain. Then one of:

| Option | Effect |
|---|---|
| **A — move Story 6.1 (outbox + drain) into Epic 3** | Epic 3 genuinely meets its own goal. Epic 6 keeps auto-send, business hours, and bounces |
| **B — reorder Epic 6 before Epic 3** | Clean, but delays every visible feature behind sending infrastructure |
| **C — accept that Epic 3 cannot send** | Honest, but then **Epic 3's goal statement is wrong** and should be amended rather than quietly unmet |

**A is recommended.** The outbox is roughly one story, it is the single thing standing between Epic 3 and its stated purpose, and splitting "enqueue" from "drain" across four epics is how a product ends up demoable and unusable.

## Tasks

*Written assuming option A. If the PO chooses C, ACs 2–5 move to Epic 6 and this story becomes the composer alone.*

### Task 1 — The composer (AC1)

- [ ] **Plain text with basic formatting.** Front-End Spec §12 rejects a rich-text editor explicitly, on the 200KB client budget Story 1.6 now enforces — a budget decision as much as a scope one.
- [ ] Both HTML and text parts, consistent with each other.

### Task 2 — Enqueue, do not send (AC4, AC5)

- [ ] Write an `outbound_messages` row with `scheduled_for = now() + <undo window>`. Architecture §9.5 delta 3 made send-undo and the auto-send delay the same mechanism, so using it here gives manual replies undo for free.
- [ ] AC5's "appears immediately" is the optimistic row plus a `conversation_events` entry when it actually sends. **Do not display "Sent" before the drain has sent it.**
- [ ] `first_response_at` set **on send, not on enqueue** — otherwise the first-response metric in §1.4 measures typing speed.

### Task 3 — Signature (AC3)

- [ ] Appended and previewable. The canonical implementation is Story 6.2 AC3 — **call it, do not duplicate it.**
